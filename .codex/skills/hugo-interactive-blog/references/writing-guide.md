# 写作指南

本指南用于把一个想法、素材或草稿发展成适合长期维护的 Hugo 知识型博客文章。它吸收既有交互页写作经验和费曼式讲解的优点，但不默认生成全量单文件 HTML。

## 核心判断

这类文章的质量不取决于字数，而取决于读者读完后能不能形成一个可复述、可迁移、可验证的心智模型。

写作时先澄清三个问题：

- 这篇文章要让读者看懂什么核心机制、关系、流程或状态变化？
- 哪些部分用文字讲会变得绕，应该改成图、表、流程、时序或交互？
- 哪些内容需要长期维护，应该留在 Markdown 和 shortcode 里；哪些局部机制只有交互形式才讲得清，需要补充 HTML/CSS/JS？

## 写作原则

- 先讲人话，再引入术语。先给直觉、例子和结构，再给定义、公式或实现细节。
- 每篇文章围绕一个核心问题展开，不写百科摘要，不把搜索到的信息线性堆上去。
- 复杂知识按“输入 -> 过程 -> 输出”、“状态 -> 事件 -> 变化”、“问题 -> 约束 -> 取舍”来组织。
- 示例要真实、最小、可验证；不要为了完整而引入大而散的示例。
- 能用图表达的，优先画图；能用交互图表达的，用少量文字引导读者操作和观察。
- 文字负责串联主线、解释关键观察和给出边界，不重复描述图里已经能看见的内容。
- 结尾要帮助读者收束成一个可复述模型，而不是只做泛泛总结。

## Hugo 表达阶梯

优先选择最容易长期维护的表达层级：

- Markdown：承载文章主线、上下文、关键解释、例子、边界和结论。
- Shortcode：承载 Hugo/Blowfish 已支持的图文表达，例如 `mermaid`、`chart`、`figure`、`gallery`、`tabs`、`steps`、`timeline`。
- 局部 HTML/CSS/JS：只在读者需要拖动、切换、调参、播放或观察动态反馈时加入，范围尽量限定在一个小节或一个演示。
- 完整交互页：只有用户明确要求，或整篇文章的理解依赖连续交互体验时才使用；否则不要让普通文章退化成难维护的单文件 HTML。

不要因为会写 HTML 就把普通文章做成一个巨大单文件。Hugo 的价值在于把长期文本、主题组件、资源和交互拆开维护。既有单文件交互页经验只能作为写作和验证原则来源，不作为默认流程或自动依赖。

## 视觉与交互选择

按表达目标选择媒介：

- 结构关系、模块依赖、调用链：优先 `mermaid` flowchart 或架构图。
- 时间顺序、请求生命周期、消息传递：优先 `mermaid` sequence diagram 或 `timeline`。
- 状态机、算法步骤、协议流转：优先状态图；如果读者需要逐步播放或改参数，再做交互页。
- 概念对比、方案取舍、参数差异：优先表格、`tabs`、`accordion` 或 `chart`。
- 多图说明、截图讲解、视觉材料：优先 `figure`、`gallery` 或页面资源。
- 可变参数、动态反馈、模拟过程、可视化推演：使用文章级 HTML/CSS/vanilla JS。

交互组件必须回答一个明确问题，例如“这个参数变大后结果怎么变”“这一步状态如何流转”“这个队列为什么会阻塞”。避免只为了显得高级而加入动效。

## 默认文章骨架

不要机械套模板，但可以按这个顺序组织初稿：

- 开头：点明读者会遇到的真实问题，以及本文要建立的心智模型。
- 第一张图或第一个可视化：尽早展示核心关系、流程或输入输出。
- 主干解释：按流程、状态或因果链讲，不按资料来源堆段落。
- 最小例子：用一个小而真实的例子把抽象概念落地。
- 深入细节：只补理解主干所需的术语、实现、公式或源码。
- 交互/图表：让读者自己观察关键变化，不让文字独自承担解释压力。
- 边界和误区：说明什么时候适用，什么时候会误解或失效。
- 收束：用短段落复述心智模型，给出可带走的判断方法。

## 读者体验底线

- 首屏要直接进入主题本体，不做空泛开场。
- 长段落要拆成图、表、步骤、对比或代码块。
- 图和交互要贴近正文位置，不要让读者在页面间来回找。
- 默认使用清晰、适合长时间阅读的视觉风格；除非主题需要，不做大面积暗色 dashboard、霓虹科技屏或装饰性动画。
- 对复杂交互，提供合理初始状态、重置能力和可见反馈。
- 移动端和桌面端都要能阅读和操作，文字、控件、图形不得重叠。
