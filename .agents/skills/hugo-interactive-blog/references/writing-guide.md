# 写作指南

本指南用于把一个想法、素材或草稿发展成适合长期维护的 Hugo 知识型博客文章。核心形态是 Markdown + Blowfish shortcode + 必要的文章级 HTML/CSS/JS 局部交互，目标是让读者建立可复述、可迁移、可验证的心智模型。

## 核心标准

好文章不是信息多，而是读者读完能复述、能判断、能迁移、能排错。

动笔前先写下四句话：

- 读者是谁：默认是想把工具用起来的实践者。
- 主问题是什么：这篇文章只回答一个核心问题。
- 读完能做什么：读者应能完成一个具体动作，例如接入、配置、排障或判断取舍。
- 第一张图表达什么：用图先展示结构、流程、状态或输入输出，不让长段文字承担所有解释。

如果这四句话写不出来，先收束主题，不要开始写正文。

## 知识教程模式

当用户给出知识点、工具、框架集成或散乱材料时，默认目标是写出一篇能快速建立心智模型的文章。不要把官网文档、搜索结果、源码发现和零散知识点平均摊开。

开头优先回答：

- 它解决什么真实问题？
- 它和读者已知方案有什么不同？
- 什么时候该用，什么时候不该用？
- 读者跟着文章能跑通哪条最小路径？

主线按主题选择：

| 主线 | 适合主题 | 写法 |
| --- | --- | --- |
| 过程链 | 请求、任务、部署、生命周期 | 按时间顺序展示输入、过程、输出 |
| 结构链 | 架构、组件、工具链 | 先给组件地图，再逐个解释职责和连接 |
| 因果链 | 一个机制推出多个现象 | 先讲第一因，再讲后果、边界和坑 |
| 对比链 | 相近概念、方案选择 | 用反例和差异解释什么时候该用 |
| 决策链 | 配置、调优、排障 | 先给判断标准，再给操作和验证方法 |

工具/库教程默认顺序：

1. 读者问题：为什么需要它，不用它会怎样。
2. 组件地图：有哪些角色，它们怎么交互。
3. 最小可运行路径：安装、文件结构、关键代码、启动命令。
4. 关键配置：每个配置解决什么边界。
5. 常见坑：症状、原因、检查点、修复方向。
6. 原理补充：只讲理解和排障必须知道的内部机制。
7. 收束：用检查表或短段落复述心智模型。

## 费曼讲解

- 先讲人话，再引入术语；术语保留英文原名，并在首次出现时讲清。
- 先给直觉、例子和结构，再给定义、公式、配置或实现细节。
- 每个抽象概念都要落到一个可观察对象：图、表、命令输出、状态变化、最小例子或交互 demo。
- 不要用“显然”“很简单”“本质上就是”跳过解释。读者真正需要的是判断标准。
- 对复杂知识，优先用“输入 -> 过程 -> 输出”、“状态 -> 事件 -> 变化”、“问题 -> 约束 -> 取舍”组织。
- 结尾不要泛泛总结，要让读者能用一句话复述核心模型。

## 表达方案

动笔前先列一张表达分工表，决定每种形式承担什么。不要先写满正文再补装饰。

| 表达形式 | 应该承担的责任 |
| --- | --- |
| Markdown | 串联主线、解释观察、给出边界和判断方法 |
| Mermaid / 图表 | 展示结构、流程、状态、调用关系或组件协作 |
| Tabs / steps / accordion | 分层展示文件、步骤、场景、坑点或方案差异 |
| HTML/CSS/JS demo | 让读者通过切换、拖动、播放、重置来观察机制变化 |
| 代码块 | 给可迁移的最小实现，不承担全部解释责任 |

如果主题天然包含流程、状态、队列、生命周期、调度、参数变化或故障分支，默认先设计一个可观察 demo。demo 不需要大，但必须回答一个明确问题。

## 图文与交互

按表达目标选择媒介：

- 组件关系、模块依赖、调用链：优先 Mermaid flowchart、feature-grid 或结构表。
- 请求生命周期、消息传递、任务执行顺序：优先 Mermaid sequence diagram、timeline 或步骤图。
- 状态机、算法步骤、协议流转：优先状态图；需要逐步播放或改参数时，再做局部交互 demo。
- 概念对比、方案取舍、参数差异：优先表格、tabs、accordion 或 chart。
- 可变参数、动态反馈、模拟过程：使用文章级 HTML/CSS/vanilla JS。

Mermaid 图优先用最低风险语法：矩形节点 `A["清晰标签"]`、普通箭头 `A --> B`、短 label。不要在 label 里塞 HTML、开头点号、`@` 符号、复杂括号、复杂标点、菱形判断节点或边标签；分支含义写进目标节点 label。

交互组件必须服务理解，不服务炫技。设计前先写一句：这个 demo 让读者观察什么变化？写不出来就不要做。

## 代码与源码

工具教程先教读者怎么使用：它能做什么、怎么接入、怎么启动、怎么观察、怎么排错。需要时再讲内部结构。

- 代码示例必须最小、真实、可迁移。
- 关键代码块前先给伪代码、状态表、时序图、组件地图或文件职责图。
- 注释少而准，优先解释生命周期、进程边界、序列化、错误处理、依赖注入和资源归属。
- 不贴大段库源码。能用伪代码、流程图、状态表、组件地图讲清的，不贴源码。
- 源码只用于回答具体问题，例如“为什么这个依赖在 worker 里取不到 request header”，并默认放在“深入原理”或折叠块中。
- 不要把“读过源码”当成文章价值。读者先要会开箱、会连接、会启动、会验证、会定位问题。

## 默认骨架

不要机械套模板，但普通工具/框架教程可以按这个顺序组织：

1. 开头：从读者真实问题切入，说明读完能做成什么。
2. 先看全图：用 Mermaid、feature-grid、表格或交互 demo 展示组件和流程。
3. 先跑通：给最小项目结构、安装命令、核心文件和启动命令。
4. 拆关键点：解释关键配置、生命周期、输入输出和边界。
5. 看常见坑：用症状表或 accordion 说明原因、检查点和修复方向。
6. 补必要原理：只讲理解和排障所需的内部机制。
7. 收束：用检查表、流程图或短段落让读者带走判断方法。

## 读者体验

- 首屏直接进入主题本体，不做空泛开场。
- 第一屏附近尽量出现核心图、组件地图或可操作 demo。
- 长段落要拆成图、表、步骤、对比或代码块。
- 图和交互贴近解释位置，不让读者来回跳。
- 默认使用清晰、适合长时间阅读的视觉风格，并同时适配本站亮色和暗色外观。
- 暗色不是问题，问题是把教程做成大面积装饰性 dashboard、霓虹科技屏或无关动效。
- 深色 demo 不要用 `-webkit-font-smoothing: antialiased`，不要用整块 `opacity` 淡化文字；需要弱化时优先只降低背景饱和度或调整背景色，文字保持原色和足够对比度。
- 对复杂交互，提供合理初始状态、重置能力和可见反馈。
- 移动端和桌面端都要能阅读和操作，文字、控件、图形不得重叠。

## 交付前检查

- 去掉所有代码块后，读者还能不能说清核心机制？
- 去掉所有图和 demo 后，文章是不是只剩 API 说明？
- 第一张图是否真的帮助理解，而不是装饰？
- 代码是否服务最小可运行路径，而不是展示作者知道很多？
- 源码是否只回答了具体问题，且没有抢走主线？
- 常见坑是否给了症状、原因、检查点和修复方向？
- 结尾是否能让读者带走一个可复述、可迁移的模型？

任一答案暴露问题，先返工表达设计，再继续润色文字。
