# 写作指南

怎么把一个知识点讲明白。**用什么讲**在 [表达手册](expression-playbook.md)，这里不重复。

核心标准只有一条：好文章不是信息多，而是读者读完**能复述、能判断、能迁移、能排错**。

## 一、收束

这是最重要的一步，也是最容易跳过的一步。

材料越多越要先收束。**不要把材料平均展开成并列清单**——那样产出的是百科条目或术语表，读者读完一个概念都带不走。

动笔前写下四句话：

- **读者是谁**：默认是想把这个东西用起来的实践者，不是研究者。
- **主问题是什么**：这篇只回答一个问题。两个问题就是两篇。
- **读完能做什么**：一个具体动作——接入、配置、排障或判断取舍。
- **第一因是什么**：全文的核心机制，后面每一节都要能回扣它。

四句话写不出来，说明主题还没收住，不要开始写正文。

### 主线形态

**默认因果链。** 它最容易建立心智模型：讲清一个机制，后面所有现象都是它的后果，读者记住一件事就能推出其余。

主题确实不适合时再换：

| 主线 | 适用 | 怎么组织 |
| --- | --- | --- |
| 因果链（默认） | 一个核心机制推出一堆现象、限制或零件 | 先立第一因，再讲后果、边界和坑 |
| 过程链 | 有明确数据流或步骤序列 | 按时间顺序展示输入、过程、输出 |
| 结构链 | 架构、组件、工具链 | 先给组件地图，再逐个讲职责和连接 |
| 对比链 | 几个相近概念或方案要分清 | 用差异和反例讲清什么时候该用哪个 |
| 决策链 | 配置、调优、排障 | 先给判断标准，再给操作和验证方法 |

### 第一因要在它自己那一节被命名

踩过的坑：核心机制只出现在标题和后续章节的回指里，**在它本该被定义的那一节从没被显式命名**。后果是下一节回指了一句上一节没说过的话。

写完搜一遍：这个词在它自己那一节出现过吗？

还有一个配套问题：**收口会把第一因写回被否定的版本**。正文花一整节论证「不是 A，而是 B」，结尾检查表一压缩又变回 A。收口段落要单独对着第一因那一节校一遍。

## 二、开头

从**具体问题或真实场景**切入，不要空泛开场，不要从定义开始。

开头几段之内要回答：

- 它解决什么真实问题？不用它会怎样？
- 它和读者已经知道的方案有什么不同？
- 什么时候该用，什么时候不该用？
- 跟着这篇能跑通哪条最小路径？

第一屏附近就要出现核心图、组件地图或可操作 demo，不要让读者读三屏文字才看到第一个可观察对象。

## 三、费曼讲解

- 先讲人话，再引入术语。**术语保留英文原名**，首次出现处讲清楚——不要为了通俗把术语换成自造中文词，那样读者回到文档和报错信息里就对不上了。
- 先给直觉、例子和结构，再给定义、公式、配置和实现细节。
- 每个抽象概念都要落到一个**可观察对象**：图、表、命令输出、状态变化、最小例子或交互 demo。
- 不用「显然」「很简单」「本质上就是」跳过解释。读者卡住的地方通常正是这些词盖住的地方。
- 复杂知识优先按「输入 → 过程 → 输出」「状态 → 事件 → 变化」「问题 → 约束 → 取舍」组织。
- 结尾不要泛泛总结，要让读者能用一句话复述核心模型。

## 四、对比与反例

只讲「怎么用」的文章是不完整的。读者真正需要的是**判断力**，而判断力来自边界。

每篇至少要有一处（放在哪一节看主题）：

- **相近概念的差别**：容易混的两个东西，差在哪，各自适合什么。
- **常见误区**：读者大概率会怎么想错，为什么会这么想，实际是什么。
- **不适用场景**：什么时候不该用这个方案，该用什么。
- **取舍**：选它付出了什么代价。

反例比正例有信息量。「这样写会怎样」往往比「应该这样写」更让人记住。

给操作建议时**不要写「建议设为 X」**——没依据也不可迁移。要写**怎么判断**：上下各挪一档，观察什么指标怎么变。

## 五、伪代码与注释

这是讲机制最好用、也最容易被跳过的两个手段。

**关键代码块前先给伪代码**（或状态表、时序图、组件地图、文件职责图）。顺序是固定的：先让读者知道这段在干什么，再给真实代码。直接甩真实代码，读者会陷在语法细节里看不见机制。

伪代码怎么写：

- 用 `text` 代码围栏，不要标语言——它不是能跑的代码，标了语言反而会让人去挑语法。
- 贴近目标语言的形状，但**去掉全部噪音**：错误处理、日志、类型标注、导入、边界判断，统统删掉，只留因果主路径。
- 一段伪代码只讲一件事。讲得下两件就是该拆成两段。

真实代码怎么给：

- **最小、真实、可迁移**。删到再删就跑不起来为止。
- 注释**少而准**，只解释语法之外的东西：生命周期、进程边界、序列化、错误处理、依赖注入、资源归属。不要注释「这里定义了一个函数」。
- 不贴大段库源码。能用伪代码、流程图、状态表、组件地图讲清的，不贴源码。
- 源码摘录只用来回答一个**具体问题**，比如「为什么这个依赖在 worker 里取不到 request header」，并且默认放进「深入原理」或折叠块，不要挡住主线。
- 不要把「我读过源码」当成文章价值。读者先要会开箱、会连接、会启动、会验证、会定位问题。

## 六、默认骨架

不要机械套模板。但工具或框架类教程按这个顺序组织通常不会错：

1. **读者问题**：为什么需要它，不用它会怎样。
2. **先看全图**：组件地图、流程图或一个可操作 demo，让读者先有整体感。
3. **先跑通**：最小项目结构、安装命令、核心文件、启动命令。
4. **拆关键点**：关键配置各解决什么边界，生命周期和输入输出是什么。
5. **对比与坑**：相近方案的差别、常见误区、症状 → 原因 → 检查点 → 修复方向。
6. **补必要原理**：只讲理解和排障必须知道的内部机制。
7. **收束**：用检查表、流程图或短段落让读者带走一个可复述的模型。

## 七、读者体验

- 首屏直接进入主题本体。
- 长段落拆成图、表、步骤、对比或代码块。
- 图和交互**贴着解释位置放**，不要让读者来回跳。
- 同一个概念全文用同一个叫法。
- 「见第 N 节」这类指向写完要核一遍。
- 不要让任何一节退化成并列的名词清单——那是收束没做够的信号。

## 八、交付前检查

- 去掉所有代码块后，读者还能不能说清核心机制？
- 去掉所有图和 demo 后，文章是不是只剩 API 说明？
- 第一张图是真的帮助理解，还是装饰？
- 第一因在它自己那一节被显式命名了吗？收口有没有把它写回被否定的版本？
- 有没有至少一处对比或反例？读者知道什么时候**不该**用吗？
- 关键代码块前面有没有伪代码或结构图？
- 代码是服务最小可运行路径，还是在展示作者知道很多？
- 源码摘录是否只回答了一个具体问题，没有抢走主线？
- 常见坑有没有给到症状、原因、检查点和修复方向？
- 结尾能不能让读者用一句话复述核心模型？

任何一条暴露问题，先返工表达设计，再润色文字。**文字层面的打磨救不了结构问题。**
