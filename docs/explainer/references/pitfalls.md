# 踩坑清单

**能被脚本检查的坑不在这里**——它们已经写进 `scripts/lint.mjs` 与 `scripts/verify.mjs` 的断言里了。
往这里加条目之前先问一句：这条能不能变成一行断言？能就去改脚本。

以下是机器查不了、只能靠人记住的。

---

## 一、写代码时容易踩的

**`putImageData` 无视 `ctx.scale(dpr)`**
在做过 dpr 缩放的画布上逐像素绘制，画面只会填到左上角一块。逐像素场景必须用「后备存储 = 逻辑像素、靠 CSS 放大」的 raw 模式，配 `image-rendering: pixelated`。
（lint 已能查覆盖率，但**判断哪些地方该用 raw** 仍靠人。）

**数值退化会静默毁掉整张图**
`Math.log(0)`、除以 0、`sqrt(负数)` 产生的 `NaN` 一旦进入 SVG 坐标，**整条 polyline 消失**且不报错。调度表、对数坐标轴的端点是高发区。
处理原则：**退化点要么跳过并在图注说明，要么换坐标；不要夹一个数值糊过去**——夹出来的值（比如把 ᾱ 夹到 1e-8 让 σ 显示成 10000）是凭空造的量级，比留空更糟。

**`IntersectionObserver` 挂在零高容器上永不触发**
把懒加载挂在初始高度为 0 的空 `<div>` 上，交叉判定命中不了，内容永远不渲染。要挂在有实际高度的祖先上（通常是外层卡片）。

**`textContent` 赋值处插 HTML 会显示成标签文本**
改文案时很容易顺手加 `<b>`，结果页面上直接出现 `<b>移动的方向</b>`。改之前先确认这段是 `innerHTML` 还是 `textContent`。

**淡化不要用 `opacity`**
它会把文字一起压下去。热力图里未选中行用 `opacity:.42` 实测把文字压到 1.6:1。改成只抽背景饱和度（`filter: grayscale()`），文字保持原色。

**热力图色阶要封顶**
让文字颜色随底色深浅翻转，会在翻转点附近出现对比度断崖（实测从 6:1 掉到 2.6:1，两侧都不达标）。更稳的做法是**色阶最深处封顶**、文字恒用墨色——数值本来就同时显示在格子里，颜色只是辅助编码。

**深色底不要 `-webkit-font-smoothing: antialiased`**
它会让中日韩字形变细、更难读。深色主题还要把行高调大一档。

**图上的标签会重叠，而且只有看图才发现**
两条曲线在端点收敛到同一处、两个向量方向接近时，贴在各自端点的标签必然叠在一起。要么按各自位置错开，要么改成图例。
更根本的一点：**如果示意向量本身太接近，图想教的东西就演示不出来**——这时候要改的是那组示意数值，不是标签位置。

## 二、内容与叙事上容易踩的

**第一因会在它自己那一节缺席**
全文的核心心智模型，很容易只出现在标题和后续章节的回指里，而**在它本该被定义的那一节从没被命名**。后果是下一节回指了一句上一节没说过的话。写完先搜一遍：这个词在它自己那一节出现过吗？

**收口会把第一因写回被否定的版本**
正文花一整节论证「不是 A，而是 B」，速查表里一压缩就又变回 A。收口段落要单独对着第一因那一节校一遍。

**模拟演示必须在图注里说明**
页面上的演示往往是用公式模拟的，不是真的在跑模型。**最显眼的那个演示最容易漏标**——别的都标了，首屏反而没标，而它恰恰最容易被误读。

**「实算」这个词会帮倒忙**
写「演示均为程序化实算」，读者会理解成「页面真的在算模型」。要写「公式实算的示意，非模型输出」。

**参数归属会写错，而且会跨多节一起错**
某个控件属于哪个节点，一旦第一处写错，后面的总表、排障链、速查表会集体照抄。校对时以「实际界面上它长在哪」为准，不要以「逻辑上它该属于谁」为准。

**不要在正文里给推荐值**
「建议设为 X」既没依据也不可迁移。要给就给**怎么判断**：上下各挪一档跑三次对比，看画面跟不跟着变。

## 三、多 agent 协作

**并行作者会把你的补丁当异常还原**
在某个作者还没交付时去改它的片段，它会认为是误注入并恢复自己的版本。**等它交付后再打补丁。**

**清理指令要写死绝对路径**
说「用完删掉你自建的临时目录」，踩过一次删到父目录、整个工作目录没了。写成 `rm -rf <绝对路径>/rev3`。
配套习惯：产物一落盘就备份，每完成一组就装配一次。

**reviewer 不要直接改文件**
多个 reviewer 并行改同一个文件会互相覆盖。让它们只出清单，编排者统一应用。

**子 agent 的自述要复核，不要照单全收**
它们会说「已验证通过」，但验证方式可能有漏洞（见下一节）。关键结论自己再跑一遍。

**话题归属表只防撞车，不防漏写**
那张表列的是「某个概念归谁独占，其它人只能一句话带过」——它管的是**重复**。
但被所有人默认「别人会写」的动作会静默消失：这一篇里「下载音频」那一步，
上一站交棒时说「第一件事是把签名 URL 上的文件拉下来」，下一站接手时却说
「音频也已经落到临时目录里」，中间那一步没有任何人按四件套走读过。
而全文有四处依赖它（耗时字段、证据阶梯的一级、签名探针、失败大头的说明）。
**除了「谁独占什么」，还要列一张「谁负责什么」——把链路上每个动作点名分配到人。**
脚本查不出来，它不知道文章应该讲什么。

**两个 reviewer 会给出互相矛盾的结论**
这一篇里，事实核对说某个 dB 数准确，叙事 review 说它算错了。
两边都给了推导过程，看起来都成立。**不要按「谁更权威」选，自己算一遍。**
实算出来是前者对，后者按一个被夸大的中间值推的；但后者顺带暴露了那个中间值
本身写松了——所以也不是白报。冲突本身往往指向一处真问题，只是不在它说的那个位置。

## 四、写验证脚本自己会踩的

这些坑会让你**误判页面有 bug**，浪费的时间比真 bug 还多。

**`scroll-behavior: smooth` 与 `scrollTo` 抢时序**
脚本里连续 `scrollTo` 会被平滑滚动动画反复打断，导致截图截错位置、断言读到旧值。测试时先注入 `html{scroll-behavior:auto !important}`。（`lib.openPage` 已内建。）

**懒加载没预热就断言**
直接跳到某个 section 断言，内容还没渲染。要先全页滚一遍再回到顶部。（`lib.openPage` 已内建。）

**对比度不做 alpha 合成会误报一大片**
把半透明渐变叠层当成不透明色，实测误报 20 处、实际 0 处。要沿祖先链把带 alpha 的背景逐层合成到不透明底上。

**颜色计算值有两种格式**
`rgb(250, 249, 245)` 是 0–255，而 `color-mix()` 的计算值 Chrome 返回 `color(srgb 0.98 0.976 0.961)` 是 0–1。只按前者解析，浅色底会被读成近黑。

**标签平衡检查要先剥掉 `<script>` / `<style>`**
脚本注释里出现一句「用原生 `<details>` 承载…」就会让计数假报警。

**判据要贴着症状，不要用代理指标或命名约定**
这一篇一口气踩了三次，全是同一个毛病：
① 窄屏检查原来扫「有没有元素矩形越界」，漏掉了 `nowrap` 长串——溢出的是文本，
   没有对应元素，矩形查不到，页面却真能左右拖 23px。改成 `scrollTo(500,0)` 看
   `scrollX` 是否为正，也就是**用户能不能真的拖动**。
② 版式家族检测原来按类名找 `nav[class*=side]`，结果三篇 explainer 全被误判——
   有一篇的导航叫 spine，而它页面里另有一堆同名的内容块。改成看 shell 的
   `grid-template-columns` 是不是两列、第一列在侧栏宽度区间。
③ 取正文样本原来用「section 的第一个直接子段落」，对没有 `<main>` 的页面抓空；
   改成「第一段够长的」又抓到卡片里的嵌套段落，量出来偏窄。最后定为
   **取全页最宽的长段落**——正文一定比卡片和图注里的宽。
共同点：矩形、类名、文档顺序都是**代理指标**，会在结构变化时悄悄失真。
症状（能不能滚动）、结构（栅格几列）、极值（最宽的那个）才稳。

**深浅两种主题都要跑**
上面两个颜色相关的 bug，一个只在浅色主题暴露、一个只在深色主题暴露。工具改动后，两篇都要重跑。
