# 工作流：从选题到发布

## 0 收束主线（最重要的一步）

材料再多，先收束出**一个主问题**和**一条主线**。不要把材料平均展开成并列清单。

四种主线形态，按知识点特点选：

| 形态 | 适用 | 例 |
| --- | --- | --- |
| 因果链 | 一个核心机制推出一堆零件 | 注意力 = 可微字典查询 → 五个漏洞 → 五个补丁 |
| 过程链 | 有明确数据流或步骤序列 | 提示词 → CLIP → 潜空间 → 采样 → VAE → 图 |
| 对比链 | 几个相近方案要分清 | 若干实现路线的取舍 |
| 决策链 | 读者要做选择或排障 | 症状 → 先查什么 → 动哪个旋钮 |

**主线定了，再定第一因**：全文只能有一个第一因，后面每一节都要能回扣它。第一因必须在**它自己那一节**被显式命名——这条踩过（见 `pitfalls.md`）。

## 1 骨架契约（阻塞后续全部工作）

骨架必须由**一个人**写完，不外包。它是所有并行作者的共同依赖，出错会同时污染所有节。

产出 `.data/explainer/<slug>/skeleton.html`，含三个占位符与完整共享层，见 `skeleton.md`。同时写 `manifest.json` 定死分组、前缀、section 归属。

视觉身份**每篇重做**，从主题推导（讲 ComfyUI 就该是深色节点画布）。可复用的是分层结构与能力清单，不是配色和版式。

## 2 并行写作（chord 分组）

一次性派发全部分组，不要逐个等。每个作者拿到的输入：

- `contract.md` 全文（逐字）
- 它负责的 section 的内容要点
- 易撞话题的归属裁定表

**易撞话题裁定**是这一步最容易漏、后果最贵的东西。写作前先列一张表：某个概念归哪一节独占，其它节只能怎么提（通常是「一句话 + 指向第 N 节」）。没有这张表，同一个概念会被三个人各讲一遍，且互相矛盾。

同时给一份**不要写的数字黑名单**：没把握的论文数字、跑分、耗时、显存占用一律不写；要具体数字就当场算给读者看。

## 3 装配

每完成一组就 `assemble.mjs` 一次，不要等全部交付。理由见 README 的「工作目录」。

**并行作者仍在跑时，不要去改它的片段**——它会把你的修改当成异常并还原。等它交付后再打补丁。

## 4 并行 review（四个维度）

这四个维度抓到的问题**几乎零重叠**，缺一个就会漏一类：

| 维度 | 查什么 | 实测抓到过 |
| --- | --- | --- |
| 技术事实 | 公式方向、参数归属、跨节数值一致、编造数字 | 某参数被挂错节点，跨 4 处、与整节论点对撞 |
| 代码契约 | 命名隔离、禁用 API、canvas 正确性、数值退化 | 滑杆右端单次同步计算 363ms 卡死主线程 |
| 可访问性 | 对比度、键盘、canvas 文字读数、窄屏、减弱动效 | 淡化用 opacity 把文字一起压到 1.6:1 |
| 叙事因果链 | 导语接缝、收束交棒、清单化退化、演示诚实性 | 一个 `<div>` 用 `</p>` 闭合，会吞掉整张演示卡片 |

reviewer 只出问题清单，**不直接改文件**——多个 reviewer 同时改会互相覆盖。改由编排者统一应用。

给 reviewer 的清理指令要**写死绝对路径**（`rm -rf <绝对路径>/rev3`）。说「删掉你自建的临时目录」踩过一次：它删到了父目录。

## 5 verify

```bash
node docs/explainer/scripts/lint.mjs   <slug>
./run.sh blog build
node docs/explainer/scripts/verify.mjs <slug>
node docs/explainer/scripts/contrast.mjs <slug>
```

再对首屏与两三个重交互节 `shot.mjs` 截图人工看一眼——**排版问题只有看图才发现**：标签重叠、canvas 只填一角、宽表撑破。

最后按 `checklist.md` 过一遍机器查不了的项。
