# 《一文读懂》交互页提示词

`docs/explainer/` 是一套写「知识点 → 单文件离线交互页 → Hugo 内嵌发布」的工具集。这份文档只放**两块可整段复制的提示词**：

| 什么时候用 | 复制哪一块 | 结果 |
| --- | --- | --- |
| 要写新的一篇 | 下面的「① 使用」 | 贴在你自己那段博客需求的**前面或后面**，一起发出去 |
| 一篇写完并验证通过 | 下面的「② 更新」 | 单独发。多数时候结论是「不用动 `docs/explainer/`」 |

不用每篇都跑第 ②。它自带准入判据，**默认结论就是不改**。

---

## ① 使用：写新一篇时贴在需求旁边

原样复制，不用填空。你的选题、材料、想讲的东西照常写在它前面或后面。

```text
这篇博客用 docs/explainer/ 这套工具集来做，产出是单文件离线交互 HTML，由 Hugo 文章内嵌发布。

动手前先读这四份，按它们执行：
- docs/explainer/README.md            心智模型、目录、工作目录约定、命令
- docs/explainer/references/workflow.md   从收束主线到发布的六步
- docs/explainer/references/skeleton.md   骨架必须具备的能力（不是长相模板）
- docs/explainer/references/pitfalls.md   机器查不出来的坑

几条不要跳过的：

1. 先收束主线再动手。一个主问题、一条链（因果 / 过程 / 对比 / 结构 / 决策）、一个第一因。
   不要把材料平均展开成并列清单。第一因必须在它自己那一节被显式命名。

2. 视觉身份这一篇重新设计，从主题推导。已有两篇分别是暖白纸面加残差流脊线导航、
   深色画布加节点连线导航，不要撞脸。可复用的是分层结构、无障碍底座和脚本，不是配色和版式。

3. 骨架由你一个人写完，不外包。骨架是所有并行作者的共同依赖，它错了会同时污染所有节。
   连同 .data/explainer/<slug>/manifest.json 一起定死分组、前缀、section 归属。

4. 并行写各节时，每个作者都要拿到 docs/explainer/references/contract.md 全文（逐字，
   替换掉里面的尖括号占位），外加它负责的内容要点和易撞话题归属表。
   同一个 chord 分组的作者在同一条消息里一次性派发，不要逐个等。

5. 每完成一组片段就 assemble 一次，不要等全部写完。装配产物一落盘就是真源。

6. 宣布完成前，这四条命令必须实际跑过并全绿，只看 diff 不算：
   node docs/explainer/scripts/lint.mjs     <slug>
   ./run.sh blog build
   node docs/explainer/scripts/verify.mjs   <slug>
   node docs/explainer/scripts/contrast.mjs <slug>
   再按 docs/explainer/references/checklist.md 走一遍人工项（截图、内容、发布壳）。

7. 不要读 content/ 和 static/ 下的其它文章。这一篇独立写。
   仓库 AGENTS.md 的「仓库读取范围」也要求默认不展开这两个目录。

8. 不擅自加兜底。不要 silent catch、不要默认值吞错、不要降级渲染，让错误暴露出来。
   演示数据算不出来就明说算不出来，不要编一个数糊上去。

完成后告诉我：主线是什么、第一因是什么、每一节负责什么、四条命令的实际输出、
以及你自己拿不准需要我复核的地方。
```

## ② 更新：一篇写完之后判断要不要沉淀

**单独发，不要和写文章的会话混在一起。** 上一篇的验证结果留在上下文里最好。

```text
上一篇《一文读懂》交互页已经写完并验证通过。现在只做一件事：判断这一篇有没有
值得沉淀回 docs/explainer/ 的东西。默认结论是不用改，不要为了有产出而改。

先跑准入判据。四条里一条都不命中就直接结束，回我一句「无需沉淀」加一句理由：

A. 这一篇踩的坑，是 docs/explainer/references/pitfalls.md 里没有的新类别吗？
   同一类坑换了个地方复发，不算新类别，不要记第二遍。

B. 这个坑能不能写成断言？能就该进 lint.mjs 或 verify.mjs，不进文档。
   规则的真身是脚本，不是文字。文档一长就没人看，断言不会。

C. contract.md 里有没有某句约束，我这一篇是手动补上去的？
   连着两篇都要手动补，才说明它该进模板；只有这一篇需要，不要动。

D. 现有的某条断言，这一篇暴露出它太粗（对正常写法误报）或太松（该报没报）吗？

命中了才往下做，并且只做命中的那条：

- 命中 B 或 D：改 scripts/。改完必须拿现有全部已发布的 explainer 文章各回归跑一遍
  lint / verify / contrast，全绿才算数。
  （这条救过场：color(srgb …) 的解析 bug 只在深色文章上暴露，只测亮色那篇会漏。）
- 命中 A：往 pitfalls.md 加一条。写清楚现象、为什么会踩、怎么避开，不要只写结论。
- 命中 C：改 contract.md 或 skeleton.md，改完确认 README.md 里的描述还对得上。

不要沉淀这些：
- 只在这一篇成立的东西（和本篇主题绑死的设计决定、这个知识点特有的讲法）
- 一次性失误（打错字、路径写错、忘了跑某条命令）
- 已经被断言覆盖的（脚本已经会报了，就不要再写进文档）
- 「以后注意一下」这类没有可执行动作的话

顺带确认一次演进路线，三条同时成立就提醒我可以抽成 skill：
1. scripts/ 连续两篇没有改动
2. contract.md 连续两篇逐字可用，不需要为新主题改结构
3. 新一篇的 review 没有报出 pitfalls.md 里没有的新类别坑

最后回我：命中了哪几条判据、改了哪些文件、回归跑的实际输出、以及三条演进条件当前各是什么状态。
```

## 为什么第 ② 块要这么写

判断放在最前面、动作放在后面，是刻意的。反过来写（先讲怎么更新、再讲什么时候更新）的话，每篇收工都会变成一次文档编辑会，`pitfalls.md` 半年后会长到没人看——那就等于这套东西白做了。

「不要沉淀这些」那一节同理，挡的是「这次踩了个坑，记一笔」的冲动。文档腐化基本都是从这种无害的一笔开始的。
