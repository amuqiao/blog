消息的一次旅程

客户端侧 边界 worker 侧

    一文读懂 taskiqkiq 之后，你的函数并没有被调用

    写下 await send_mail.kiq(user_id)，这一行到底做了什么？

    它没有执行 send_mail。它把这次调用打包成了一条 JSON 消息，扔进队列就返回了。真正执行发生在另一个进程、可能另一台机器上。这条边界一旦划下，taskiq 后面所有的设计——参数为什么不能传数据库连接、worker 为什么会「找不到任务」、结果为什么需要单独一个后端、依赖注入为什么存在——都是它的直接后果。本文沿这条因果链走一遍，每处机制都配一段伪代码说明它在做什么，再对上真实 API。

      一行 .kiq()，到底做了什么

      先看一段能跑的代码。三个文件，加起来不到二十行——本文后面所有内容，都是在解释这二十行背后发生的事。

      最小可验证例子

      三步跑起来：

      注意 .kiq() 返回的那一刻

      如果 send_mail 是个普通函数，await send_mail(1) 会一直等到它执行完。但 .kiq(1) 不是——它立刻就返回了，而这时候 worker 那边可能还没开始干活，甚至 worker 根本没启动。

      返回给你的也不是函数的返回值，而是一个 AsyncTaskiqTask 对象——一张取货凭据。想拿真正的结果，还得再拿着它去问一次。

      这一行做的三件事 一、把「调用哪个函数、用什么参数」打包成一条消息。二、把这条消息扔进队列（broker）。三、返回一张凭据，凭据上只有一个 task_id。 它自始至终没有执行你的函数。

      本文讲什么、不讲什么

      taskiq 是 Python 的异步分布式任务队列。名字念作 task-i-q，你可以理解成 task queue 的一个变体写法。它和 Celery 解决同一类问题，区别是它原生基于 asyncio——任务本身就是 async def，broker 的收发也是异步的。

      本文只走一条主线：一次调用如何跨过进程边界，又如何把结果带回来。沿这条线，会依次碰到参数序列化、任务命名、类型还原、broker、结果后端、依赖注入、中间件、消息确认、worker 进程模型、定时调度、配置取舍。

      不讲的：具体某个 broker 的运维（RabbitMQ 怎么配集群之类）、Celery 的迁移细节、以及 taskiq 各插件的完整 API 清单。主干走通了，这些自己查文档就够了。

      什么是「任务队列」

      一句话：把「现在要做的事」写成一张纸条，扔进一个筐里，让另一批进程从筐里拿纸条干活。

      为什么需要它？典型场景是一个 Web 接口：用户点了「注册」，你要发确认邮件。发邮件可能耗时 3 秒还可能失败重试——如果在接口里同步做，用户就得干等 3 秒。把它变成一张纸条扔进筐，接口立刻返回，邮件慢慢发。

      那个「筐」就是 broker（消息中间件），通常是 Redis 或 RabbitMQ。从筐里拿纸条干活的进程叫 worker。

      先破一个直觉 很多人第一次用会以为 .kiq() 是「在后台线程里跑这个函数」。不是。它甚至不要求那个函数在当前进程里能跑得起来——它只是发了一条消息出去。函数在哪执行、什么时候执行、能不能执行，取决于队列另一头有没有人在听。
      本节收束「打包成消息扔出去」这句话听起来平淡，但它划下了一条边界。下一节把这条边界的真身摆出来——那条消息长什么样，以及为什么它一旦成型，后面所有设计就都被决定了。
      [ 02 · 第一因 边界 ]

      第一因：那条消息长什么样

      整篇文章只有一个第一因，就是这一节。后面十三节，全是它的后果。

      第一因 .kiq() 把一次函数调用压成了一条 JSON 消息。压得进去的东西才能过去，压不进去的东西——数据库连接、打开的文件、内存里的对象——一律过不去。 这条边界叫序列化边界。taskiq 后面的每一个设计，都是在回答「边界两侧各自该怎么办」。

      消息的真身

      taskiq 内部用一个 pydantic 模型描述这条消息。它一共只有六个字段：

      看清楚它没有什么：没有你的函数对象，没有闭包，没有 self，没有任何进程内的引用。只有一个名字和一堆能写成 JSON 的值。

      什么是「序列化」

      序列化（serialize）：把内存里的对象变成一串可以存盘、可以走网络的字节。反序列化是反过来。

      为什么内存对象不能直接发走？因为内存里的东西大多是指针——一个数据库连接对象里存的是「第 7 号 socket 文件描述符」，这个编号只在当前进程有意义。发到另一台机器上，7 号描述符指向的是完全不相干的东西，甚至根本不存在。

      所以跨进程传递只能传值，不能传引用。JSON 就是一种最常见的「只装得下值」的格式。

      [ 03 · 参数 客户端侧 ]

      参数怎么过界：三条规则

      上一节的检查台已经把结论摆出来了。这一节把规则说清楚，并解释一件容易忽略的事——有些类型能过去，但过去之后就不是原来那个东西了。

      规则一：taskiq 会替你摊平两种东西

      在打包之前，每个参数都会先过一遍 _prepare_arg。它只做两件事：

      翻译过来：pydantic 模型和 dataclass 会被摊平成 dict，其余原样放行。注意最后那句 raise——如果你传的是类型本身（比如把 User 这个类而不是它的实例传进去），taskiq 会当场报错，而不是等到 JSON 编码时才失败。

      规则二：摊平是单向的，形状会丢

      这是最容易踩的一处。User(id=1, name="a") 过界之后变成 {"id": 1, "name": "a"}——它已经不是 User 了。

      worker 侧的函数如果写成 async def f(u: User)，还能拿回 User 吗？能，但那是另一个机制在起作用（第 05 节的类型还原），不是这一步。如果参数没写类型标注，你收到的就是一个裸 dict。

      由此产生的一个真实 bug 函数签名写成 async def f(u)（没标类型），本地直接调用时 u.name 正常；换成 .kiq() 之后 worker 里 u.name 抛 AttributeError——因为此刻 u 是个 dict，只能 u["name"]。 本地调用和远程调用行为不一致，根源就在这条边界上。写全类型标注能避免绝大多数这类问题。

      规则三：过不去的东西，不要想办法「塞过去」

      数据库连接、HTTP client、文件句柄、锁——这些都过不去，而且不该过去。

      原因不是 taskiq 不支持，而是这类对象的本质就是「指向本进程某个资源的引用」。硬要序列化它（比如自己 pickle 一下），到了 worker 那边也只是一个指向不存在的东西的空壳。

      正确的做法是：只传标识，让 worker 自己去取。

      「传 id 不传对象」这条习惯，在任何跨进程场景里都成立，不是 taskiq 特有的。

      那 worker 侧怎么拿到连接它自己建一个，并且在多个任务之间复用。这件事有专门的机制承担——依赖注入，见第 08 节。这里先记住结论：连接由 worker 侧负责，不由消息携带。
      本节收束参数怎么过去说清楚了。但消息里还有一个字段没讲：task_name。worker 收到一个字符串，它是怎么找到该调用哪个函数的？——这是「worker 找不到任务」这个高频报错的全部答案。
      [ 04 · 寻址 两侧 ]

      worker 靠一个字符串找到你的函数

      消息里没有函数对象，只有 task_name 这个字符串。worker 拿到它之后要在自己进程里找出对应的函数——找得到就执行，找不到就丢掉这条消息，只打一行 warning。这一节讲清楚这个名字从哪来、为什么会对不上。

      名字默认是「模块路径 : 函数名」

      所以 app/tasks/jobs.py 里的 send_mail，默认名字就是 app.tasks.jobs:send_mail。

      对上名字需要两个条件同时成立 一、worker 进程导入过那个模块——没导入，注册表里就没有这个名字。 二、客户端和 worker 算出来的模块路径完全一致——同一个文件，从不同的工作目录导入，路径可能不一样。

      [ 05 · 还原 worker 侧 ]

      类型标注在 worker 侧被真的用上了

      在大多数 Python 代码里，类型标注只是给人和静态检查工具看的，运行时不起作用。taskiq 是个例外——它拿你的类型标注去把 JSON 里的值转回来。这一节讲清楚它怎么转、什么时候转不动。

      先看现象

      你传的是字符串 "11"，worker 里拿到的是整数 11。中间没有任何人写转换代码——是 parse_params 读了 a: int 这个标注，自己转的。

      它是怎么做的

      关键在最后那句 转不动就原样留着。这是一个刻意的设计：它不会因为类型对不上就让任务失败，只打一行 warning，然后把原值交给你的函数。

      这解释了两件事 一、pydantic 模型能「变回来」。第 03 节说过 User 过界后变成 dict——但只要函数签名写着 u: User，这一步就会用这个标注把 dict 重新解析成 User 实例。形状是靠标注补回来的，不是消息里带回来的。 二、没写标注就没有这一步。参数标成 Any 或者干脆不标，你拿到的就是 JSON 里的原始形状。

      什么时候会转不动

      想彻底关掉它worker 启动时加 --no-parse，所有参数原样交给函数。适合你自己已经做了严格校验、不希望多一层隐式转换的场景。

      为什么这个设计值得留意

      它让「跨进程调用」在写法上尽量贴近「本地调用」——你照常写 async def f(u: User)，不用在函数开头手动 User(**payload)。

      代价是多了一层隐式行为：类型转换在你看不见的地方发生，失败时只有 warning。所以真正重要的校验不要指望它——它是便利，不是保障。

      本节收束从字节到一次真实的函数调用，这条路走完了。接下来往回看基础设施：那个「队列」到底是什么，换成不同的 broker 有什么区别。
      [ 06 · broker 边界 ]

      broker：那个筐长什么样

      broker 是消息落地的地方，也是客户端和 worker 唯一的接触点。它的接口小得出奇——本质上只有两个动作。

      broker 只需要会两件事

      kick 把字节扔进去，listen 是个异步生成器，源源不断吐出字节。其余全是实现细节。正因为接口这么窄，换 broker 才是一行代码的事。

      常见的几种，以及它们的真实差别

      选型的第一个问题不是「哪个快」 是「这条消息丢了要不要紧」。 不要紧（比如刷新缓存、打点统计）→ 简单的队列就够。 要紧（扣款、发货、生成报告）→ 必须选一个支持确认机制的，也就是「worker 说处理完了，消息才真正从队列里消失」。这件事第 10 节展开。

      InMemoryBroker：不要在生产用，但测试离不开它

      taskiq 自带一个 InMemoryBroker。它根本没有队列——kiq() 直接在当前进程里把函数跑了。

      这在写测试时非常有用：不用起 Redis、不用起 worker，await task.wait_result() 立刻就有结果。

      但它也会掩盖问题：因为根本没过序列化边界，那些「传了不能序列化的对象」的 bug，在 InMemoryBroker 下全都测不出来，一上真 broker 就炸。测试里最好至少有一条用例走真实 broker。

      Redis 的 List 和 Stream 有什么不同

      List 是最朴素的队列：LPUSH 塞进去，BRPOP 取出来。取出来的那一刻，消息就从 Redis 里没了——worker 中途崩溃，这条消息也跟着没了。

      Stream 多了一个「消费组」的概念：消息取走之后仍然留在 Stream 里，标记为「已投递、待确认」。worker 处理完显式确认（ACK），它才算真正完成；worker 崩了没确认，这条消息可以被重新投递给别人。

      代价是 Stream 要额外管理消费组、要处理「待确认」堆积，运维上比 List 复杂。选哪个，回到上面那个问题：这条消息丢了要不要紧。

      本节收束消息发得出去了。但 .kiq() 返回的只是一张凭据——结果是怎么从 worker 那边传回来的？下一节讲结果后端，以及一个很多人第一次就会撞上的坑。
      [ 07 · 结果 两侧 ]

      结果不走原路回来

      这是新手最容易撞的一处：队列是单向的。消息能过去，返回值回不来——它要走另一条道，那条道叫 result backend。

      为什么不能原路返回

      想想那个筐。你往筐里扔了一张纸条就走了，worker 过了三十秒才拿到、又花了五秒办完。这时候它拿着结果，要交给谁？你早就不在那儿了——发起调用的那个 HTTP 请求可能已经返回，那个协程可能已经结束。

      所以结果只能存到一个双方都能访问的地方，由你事后凭 task_id 去取。这个地方就是 result backend，通常也是 Redis。

      凭据与取件

      wait_result() 不是「被通知」，而是轮询——每隔一小段时间去问一次 result backend「好了没」。看源码：

      默认间隔是 秒。这意味着两件事：结果最快也要等到下一次轮询；以及 timeout 默认是 −1，即永远等下去——生产代码里几乎总该显式传一个超时。

      拿回来的是什么

      注意 is_err：任务里抛的异常不会在你这边重新抛出来，而是被打包进结果对象。想让它抛，得自己判断 is_err 或者用 result.raise_for_error() 这类方式处理。

      最常见的三个坑 一、没配 result backend 就调 wait_result()。默认的后端不存结果，你会一直等到超时。 二、把 wait_result() 写在 Web 接口里同步等。那就等于把异步又变回了同步，还多了一趟网络——如果非要等，为什么要用队列？ 三、结果不会永远留着。Redis 后端通常配了过期时间，过期之后 task_id 就查不到东西了。要长期保存，写你自己的数据库。
      那什么时候该等「立刻要给用户一个答复」的场景本来就不适合用队列。队列适合的是：发出去就不管了（fire and forget），或者过一会儿再回来查（前端轮询一个状态接口）。真正需要「等」的地方，往往说明这件事根本不该异步化。
      本节收束去和回的路都通了。现在回到第 03 节留下的那个悬念：数据库连接过不去，worker 侧到底怎么拿到它？
      [ 08 · 依赖注入 worker 侧 ]

      过不去的东西，在那边现造

      数据库连接不能过边界，但任务又确实要用它。taskiq 的答案很直接：别传，让 worker 侧自己造。造的时机、复用、清理，交给一套依赖注入机制管——写法和 FastAPI 几乎一样。

      这一节和第一因的关系 依赖注入不是「一个方便的特性」，它是序列化边界的直接产物。 边界只让值过去 → 连接类对象过不去 → 但任务需要它 → 所以必须有一个「在 worker 侧按需构造」的机制。 反过来看也成立：凡是你想 .kiq() 却传不过去的东西，八成都该改成依赖。

      三种资源，三种放法

      为什么不用全局变量就好了

      直接写个模块级全局变量当连接池，也能跑。但有三个问题：

      一、测试难替换。依赖可以在测试里被整体替换成假的，全局变量得靠 monkeypatch。

      二、生命周期不明确。全局变量什么时候建、什么时候关、异常时要不要回滚，都得你自己写。依赖用 yield 把这件事表达清楚了。

      三、每个任务的独立性。数据库会话通常应该「一个任务一个」，用完就关；全局共享一个 session 会带来事务串味的问题。

      全局变量适合的是真正全局且无状态的东西，比如一个 HTTP client 连接池——那种情况可以放在 worker 启动事件里初始化，见下一节。

      本节收束任务执行需要的一切都齐了。接下来看一类横切的东西：重试、日志、埋点这些「每个任务都要做一遍」的逻辑，该挂在哪。
      [ 09 · 中间件 两侧 ]

      八个钩子，分别长在哪一侧

      重试、日志、埋点、链路追踪——这些「每个任务都要做一遍」的事，写进每个任务函数里就重复了。taskiq 把它们抽成中间件，一共八个钩子。理解它们的关键不是记住名字，是搞清楚每个钩子跑在边界的哪一侧。

      八个钩子的位置

      点任意一个钩子，看它在什么时刻、在哪一侧被调用，以及适合在里面做什么。

      一条分界线 pre_send / post_send 跑在客户端进程里——是发消息的那一侧。 pre_execute / post_execute / post_save / on_error 跑在worker 进程里。 startup / shutdown 两侧都会跑，靠事件类型区分是哪一侧。 写中间件时先问自己：这段代码需要访问的东西，在这一侧存在吗？

      [ 10 · 确认 worker 侧 ]

      什么时候说「这条我处理完了」

      worker 从队列取走一条消息之后，要在某个时刻告诉 broker「这条可以删了」。这个动作叫 ack（确认）。什么时候 ack，直接决定了系统在崩溃时是丢任务还是重复执行——这是任务队列里最经典的一个取舍。

      先想清楚：为什么需要确认这个动作

      假设没有确认——消息一被取走就从队列删除。worker 取走了、正在跑，这时候进程被 kill 了。这条消息已经不在队列里，也没有人在处理它。它消失了。

      所以要有一个「暂存」状态：取走但未确认。worker 崩了，broker 发现这条消息迟迟没被确认，就重新投递给别人。

      at-least-once 与 at-most-once

      这是分布式系统里的一对基础概念：

      at-most-once（至多一次）：宁可丢，不可重。取走就删，崩了就没了。

      at-least-once（至少一次）：宁可重，不可丢。处理完才删，崩了就重投——可能造成同一个任务被执行两次。

      还有个 exactly-once（恰好一次），在跨进程场景里做不到（严格说是代价极高且需要业务配合）。实践中的做法是：选 at-least-once，然后把任务写成幂等的——执行两次和执行一次结果相同。

      幂等具体怎么写

      核心是：用一个业务上唯一的键，先占位再执行。占不到说明已经有人在做或做过了，直接返回。这个键最好来自业务本身（订单号、attempt_id），不要用 task_id——上一节说过，重试会换一个新的 task_id。

      [ 11 · worker worker 侧 ]

      worker 的两层并发

      taskiq worker broker:broker 这一条命令，起的其实不止一个进程。搞清楚它的并发模型，才知道「我能同时跑多少任务」这个问题该怎么算。

      两层，别混在一起

      第一层是进程。--workers 决定 fork 出几个子进程，默认 个。它们各自独立、互不共享内存，靠这个吃满多核。

      第二层是协程。每个子进程内部跑一个 asyncio 事件循环，--max-async-tasks 决定这个循环里最多同时有几个任务在飞，默认 。

      同时在跑的任务数 理论上限 = --workers × --max-async-tasks。默认就是 个。 但这个数只对 I/O 密集的任务有意义——协程并发的前提是任务大部分时间在 await（等数据库、等 HTTP）。

      为什么 CPU 密集的任务会毁掉这个模型

      asyncio 的并发是协作式的：一个协程只有在 await 的时候才交出控制权。如果你的任务里有一段纯 CPU 计算（图像处理、大量 JSON 解析、加密），那段时间它不会 await，整个事件循环就卡在那里——同进程里另外 99 个任务全都动不了。

      taskiq 对同步函数有专门处理：如果你的任务是普通 def 而不是 async def，它会被丢到线程池里跑，不阻塞事件循环。所以遇到 CPU 密集或者只有同步 API 可用的场景，写成同步函数反而是对的。

      更重的计算可以用 --use-process-pool 走进程池。

      协作式并发 vs 抢占式

      抢占式（操作系统的线程）：跑到一半会被系统强行打断，让别的线程上。你不需要做任何配合。

      协作式（asyncio 的协程）：只有你主动 await 才会让出。好处是切换开销极小、没有锁的烦恼；坏处是一个不让出的协程能饿死所有人。

      所以「asyncio 很快」有个前提：任务是 I/O 密集的。纯计算场景下它不但不快，还会因为阻塞事件循环而更糟。

      几个和稳定性直接相关的开关

      prefetch：一把抓多少条

      --max-prefetch 控制 worker 一次从队列预取多少消息。预取多了吞吐更高（少几次网络往返），但被预取的消息实际上已经离开队列、握在这个 worker 手里——它崩了，这些消息要等超时重投；而且别的空闲 worker 也拿不到它们，负载会不均。

      本节收束worker 怎么跑清楚了。还剩一类任务没讲：不是被谁调用，而是到点自己跑的。
      [ 12 · 调度 客户端侧 ]

      调度器只干一件事：到点替你 kiq

      「每天凌晨三点跑一次对账」这类需求，taskiq 用一个独立的进程解决。它的实现比你想的简单得多——看懂它做的是什么，很多关于定时任务的困惑会一起消失。

      它的全部逻辑

      就这些。调度器不执行任何任务，它只是一个「按时间表按下 kiq 按钮」的机器人。任务照样进队列、照样由 worker 执行。

      源码里那一句

      可以看到它确确实实就是构造了一个 kicker 然后 .kiq()——和你在业务代码里手写的调用走的是同一条路。

      这个设计带来三个直接后果 一、调度器和 worker 是两个进程，要分别启动：taskiq scheduler 和 taskiq worker。只起 worker，定时任务永远不会触发。 二、调度器不能多开。起两个调度器，同一个时间点就会 kiq 两次——定时任务被执行两遍。 三、定时任务的所有约束和普通任务完全一样。参数照样要过序列化边界，找不到任务照样静默跳过。

      一个容易忽略的运维问题

      调度器停机期间错过的任务，不会补跑 调度器的逻辑是「现在这一秒到点了吗」。如果它在凌晨 2:50 挂了、5:00 才拉起来，那么 3:00 那次对账就是没跑，没有任何补偿机制。 需要「一定要跑到」的任务，得自己做记账：任务开始时记一笔，另有一个巡检去发现「今天该跑的还没跑」。
