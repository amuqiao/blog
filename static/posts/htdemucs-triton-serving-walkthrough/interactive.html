    一文读懂 htdemucs on Triton从一个模型目录，到一次人声分离

    /v2/health/ready 返回 200 之后，凭什么说这个服务真的能分离音频？

    这是一条走通了的链路：四个约 302 MiB 的 ONNX 模型加一个 Python 编排层，放在 OSS 上，由 PAI-EAS 的 Triton 容器挂载运行。本文沿着这条链路走一遍——目录怎么被读、容器怎么起、每一层「就绪」各自证明了什么、一条请求进来之后经过谁的手、以及跑起来之后该看哪些数。每一站都给出代码在哪、它做了什么、为什么必须这么做、这一站坏了长什么样。

    链路目录
      [ 01 · 主问题 ]

      ready 返回 200，到底证明了什么

      部署平台把实例标成运行中，健康检查一路绿灯，日志最后一行是 Started HTTPService。此刻你手上唯一的硬证据是一个 HTTP 状态码；而你真正想知道的是另一件事——把一首歌扔进去，它会不会吐出一条干净的人声轨。这两件事之间隔着的所有东西，就是这一篇要走完的路。

      Triton 启动时做的事是确定的：扫描 --model-repository 指向的目录，为每个模型挑出版本，交给对应后端装载。全部装载成功，/v2/health/ready 才翻成 200。所以这个 200 是一句关于装载态的断言——文件在、目录名合法、后端认得这种文件、配置能解析。端点之间的分层语义留到 07 · 就绪，这里只需要接受一件事：它断言的是文件，不是结果。

      200 直接断言的
      模型仓库被成功扫描；每个模型都选出了版本；对应后端完成装载；Python backend 的 initialize() 已经返回。
      200 完全没碰过的
      客户端送来的张量形状对不对得上；编排层 execute() 里那条流水线跑不跑得通；对象存储的凭证与桶权限是否可用；一整首歌处理到一半会不会失败。

      为什么装载成功推不出可用？因为这条链路根本不是「一个模型收一段音频、吐一段音频」。请求先落到一个用 Python 写的编排层，它去取音频、把音频整理成模型要的形状、反复调用四个独立的 ONNX 模型、把一堆中间结果拼回一条完整音轨、再写回对象存储。装载期只走到「这些代码和权重都在」，往后每一步都要等第一次真实请求才第一次被执行。凭证过期、桶名写错、形状差一维、编排层里某个分支从没跑过——这些故障发生的位置，/v2/health/ready 一次都没有路过。

      所以本文不去论证「它应该能用」，而是把这条路拆成 17 站，每一站回答四个问题：代码在哪、它做了什么、为什么必须这么做、这一站坏了在外部长什么样。下面这张图就是全程；点任意一站可以直接跳过去。

      地图分成四段，分界线是时间。前三站是读懂对象本身：主问题、音频量纲、模型目录。中间四站是部署期——请求还没来，容器已经在做的事：解析配置、挂载存储、拉起进程、装载权重、给出各层的就绪信号。再往后七站是请求期——从第一次主动打一发探针开始，一条请求依次经过的手。最后三站是运行期：服务活着的时候该看什么、坏了怎么认出是哪一站坏的。绝大多数「部署成功却不能用」的故障，就卡在第 07 站和第 08 站之间那道缝里：07 之前全是声明与装载，08 是整条链路上第一次真的执行。声明能验证的东西到 07 为止，再往后的每一步都要等一条真实请求才第一次被跑到。

      全链路 17 站　左侧是请求到来之前就已经决定好的事，右侧是一条请求进来之后依次发生的事。悬停或聚焦任一站会在下方显示它的职责。

      把指针停在任意一站上，这里显示它负责什么。

      这次的具体对象
      容器里 /models 下有 5 个模型目录：4 个 htdemucs_ft_*，各自带一份 model.onnx（单份 …，四份合计 …）；1 个 audio_stem_separation_pipeline，里面是 Python 代码而不是权重。运行环境是 PAI-EAS 上的 Triton 25.03-py3 镜像，1 张 GPU、8 CPU、30 GB 内存，单实例。整篇文章讲的都是这一套东西。
      本站收束200 是一句关于文件的断言，不是关于结果的断言。要判断服务能不能用，只能从 Triton 读到的第一样东西开始查——那是一个目录。但在看懂目录里放的是什么之前，先把音频这一侧的量纲摆平。
      [ 02 · 基础 ]

      音频的最小心智模型：44100、2、[-1, 1]

      后面每一站都会反复出现同一批数字：44100、2、float32、样本数。它们不是这套服务的设计偏好，而是「声音怎么变成数组」这件事本身带来的约束。这一站把这些量纲从头推一遍——往后再遇到任何一个形状、体积或时长，你都能自己算出来，不用记。

      采样：一秒钟取 44100 个数

      声音在空气里是连续变化的气压。计算机存不了连续量，只能按固定间隔去「量一下现在是多少」，把结果记成一个数。每秒量多少次，就是采样率（sample rate），单位 Hz。这套服务里它恒等于 TW.K.SR = …，意思是一秒钟的单声道声音就是这么多个数排成一列。

      采样率不是越省越好，也不是越高越好，它决定的是哪些成分还能被还原出来。下面这张图把同一条正弦波在不同采样率下的采样点画出来：拖低采样率，点会变稀；稀到一定程度，把这些点连起来得到的已经不是原来那条波，而是一条频率更低的假波。

      采样与还原（示意，非真实音频数据）　细灰线是理想中的连续波形，圆点是采样点，绿线是把采样点直接连起来的还原结果。橙色虚线只在发生折叠时出现，它是这些采样点实际对应的那条低频波。波形由页面按公式生成，不是任何一段真实录音。

      为什么偏偏是 44100

      一条频率为 f 的成分要被采样点唯一确定，采样率必须严格高于 2f；低于这个门槛，它会折叠成一条更低频的波，而且从采样点上再也分不出原来是哪一条——上面那张图把这件事画出来了，把采样率拖到波形频率的两倍以下就能看到。人耳能听到的上限通常按 20 kHz 计，于是采样率至少要到 40 kHz 以上。44100 是 CD 时代定下并沿用至今的取值，htdemucs 这一族模型也按它训练，所以整条链路里它是一个固定值而不是可调项。

      声道、位深、时长：三个换算

      剩下三件事各自只有一行算式，但它们决定了后面所有张量的形状和所有内存估算。下面三页分别是：立体声在内存里怎么排、16-bit 整数怎么变成 float32、以及时长怎么换成样本数和字节数。三页的数都由页面当场算，没有写死的常数。

      页面上的每一个数都从 TW.K.SR 与 16-bit 的定义推出，可以自己按算式核对。

      位深与量化误差

      16-bit 的含义是每个采样点只有 216 = 65536 个可取值。真实幅度落在两个可取值之间时必须就近取整，这个取整偏差叫量化误差，它是位深本身带来的、与采样率无关的一种失真。位深越高，格子越密，同一个幅度能被记得越准，代价是每个采样点占的字节数线性变多。这条链路里输入按 16-bit PCM 解析，进内存后统一变成 float32 参与计算，两者是不同的事：前者是存储格式，后者是计算格式。

      什么是 stem

      一首成品歌曲是若干声源叠在一起的结果：鼓、贝斯、人声、其它乐器，各自是一条独立的信号，混音时按样本逐点相加，最后只留下相加后的那一条。stem 这个词来自混音工程，指按声源或分组单独导出的那些分轨。你手上的 mp3 或 wav 里没有 stem，只有相加后的结果。

      所谓音轨分离，就是反过来做这件事：只给你相加后的一条，让你估计出加之前的各条。这是个欠定问题——同一条混音在数学上可以由无穷多组分轨相加得到，模型给出的是它认为最合理的那一组，而不是唯一解。这套服务最终对外只给两轨：vocals（人声）和 background（其余部分之和）。

      叠加与分离（示意，非真实音频、非模型输出）　波形用固定种子的伪随机数与正弦函数合成，仅用于说明「相加」和「拆开」这两个方向，不代表任何真实录音的形态，也不是这套模型的实际输出。

      读数加载中。

      本站收束记住三条：一秒 44100 个数、立体声是两行不是两列、每个数落在 [-1, 1) 里。后面出现的每一个形状、每一段体积、每一次时长换算，都能从这三条推出来。下一站回到那个目录，看 Triton 到底是怎么读它的。
      [ 03 · 目录 ]

      Triton 眼里的这个目录

      Triton 不认识 htdemucs，也不认识人声分离。它认识的只有一套目录约定：哪一层是模型名、哪一层是版本、版本里放什么文件。这次挂进容器的是 OSS 上的 .../releases/htdemucs/，所以 /models 下不多不少就是五个目录。这一站把它们逐个拆开。

      约定只有两条，但它们解释了这个目录为什么长成这样。第一条：模型仓库的第一层子目录名，就是模型名。请求里 /v2/models/htdemucs_ft_vocals/infer 的那一段，不是配置文件里另外声明的别名，就是这个目录的名字。第二条：模型目录的下一层必须是纯数字的版本目录。1/ 里放的才是真正的模型内容。这两条合起来的含义是——在 Triton 里，「一个模型」不是一个文件，而是一个按约定命名的目录。

      这套约定听上去只是文件摆放规矩，实际决定了两件事。其一，目录名就是 API：把 htdemucs_ft_vocals 改成别的名字，所有调用方的请求路径当场失效，而且没有任何配置项能把旧名字映射回去——它不是配置，它是文件系统事实。其二，版本是目录不是标签：同一个模型目录下可以并排放 1/ 和 2/，Triton 按版本策略决定装载哪个，所以「换一版权重」这件事在仓库里的物理形态就是多放一个数字目录。反过来，某个模型目录漏了数字那一层，性质不是「配置写错了」，而是「Triton 认为这个模型没有任何可用版本」。

      挂载后的 /models　点目录展开或收起，点任意节点在右侧看它是什么、Triton 拿它做什么、缺了会怎样。体积由 TW.K.ONNX_BYTES 换算，不是估的。

        把树展开一遍会看到一件容易被略过、但后面所有事情都建立在它上面的事实：这五个目录里，四个装的是权重文件，一个装的是源代码。htdemucs_ft_* 交给 onnxruntime 后端，Triton 直接把计算图跑起来；audio_stem_separation_pipeline 交给 Python backend，Triton 为它起一个独立的 Python 进程，import 那个 model.py。两类东西的加载方式、执行方式、失败方式都不一样，但它们摆在同一个仓库里，对外用同一套 HTTP 协议、同一套 URL 形状，客户端从外面看不出区别。

        还有一点得先记住：这五个目录之间没有任何声明式的依赖关系。从仓库里看不出 audio_stem_separation_pipeline 会去调用那四个 htdemucs_ft_*，Triton 也不知道这回事。这层关系只存在于 model.py 的代码里，靠模型名的字符串硬连。所以万一少了一个 ONNX 目录，Triton 照样把剩下的都装载好，真正的失败要推迟到编排层去调用那个不存在的名字时才发生——这正是 01 · 主问题 里那条缝的一个具体样本。

        同一个仓库、同一套 URL 形状，底下是两种完全不同的执行体：一种是被 onnxruntime 装载的计算图，一种是被 import 的 Python 类。

        体积
        单份 model.onnx 是 …，四份合计 …。这个数字在冷启动那一站会再出现一次：容器每次起来，这些字节都要从挂载点读进去。这里只给体积事实，读它花多久是 06 · 冷启动 的事。
        本站收束模型在 Triton 里不是一个文件，是一个按约定命名的目录：第一层是名字，第二层是版本，第三层才是内容。五个目录里四个交给 onnxruntime、一个交给 Python 进程，对外却是同一套协议。下一站进到每个目录都有的那份 config.pbtxt，看这份声明到底写了什么。
        [ 04 · 契约 ]

        config.pbtxt：两份文件，两种装载方式

        上一站把 /models 下的目录摆清楚了，但目录名只回答了「这个模型叫什么」。Triton 打开目录之后还要知道：用哪条路径把它装进内存、进出的张量叫什么名字、是什么类型、什么形状、放在哪块设备上。这些答案全部写在每个模型目录根部的 config.pbtxt 里。这一站把其中两份真实配置逐字段拆开——一份 ONNX，一份 Python。

        两份 config.pbtxt 原文，逐行可点。选中一行会在下方展开这个字段的三件事：Triton 拿它做什么、写错会怎样、这条规矩是 Triton 的还是这个仓库自己加的。区分后两者是本站的重点。

        为什么一个写 platform，一个写 backend

        这两个键不是同一件事的两种写法。platform: "onnxruntime_onnx" 让 ONNX Runtime 去读版本目录里的 model.onnx，把它变成一个推理 session；backend: "python" 让 Python backend 起一个解释器进程，导入版本目录里的 model.py，实例化里面的模型类。目录里放的东西不一样，负责装载的人也不一样，所以键名不一样。仓库的校验脚本就是按这条分叉写的：runtime 是 python 就检查 backend: "python" 这一行，否则检查 platform: 那一行（scripts/lib/manifest.py:213-216）。

        max_batch_size: 0 不是「批大小等于 0」

        当 max_batch_size 大于 0 时，Triton 把 dims 理解成「去掉批维之后的形状」，真实张量前面还会多出一个由 Triton 管理的维度，它可以把多个请求拼进同一次 forward。写 0 的意思是：这个模型没有批维，dims 写的就是完整形状。

        所以 [ 1, 2, ] 里的那个 1 是模型自己固定死的第一维，不是 Triton 的批维度。两个请求同时到达时，Triton 不会把它们合成 [2, 2, …]，只会排队，一个一个过。

        后两维是可以当场读懂的：2 是声道数， 是一段音频的采样点数——按 Hz 采样率折算是 秒。为什么偏偏定这个长度、一首几分钟的歌怎么被切成若干段喂进来，是第 11 站的事，这里只需要接受一件事：这个数字是写死在契约里的，请求的形状差一个采样点都不行。

        一条 Triton 允许、这个仓库禁止的开关

        Triton 本身允许你在 config.pbtxt 里加 dynamic_batching 让它自动攒批。这个仓库不允许：校验脚本对整份配置文本做一次子串匹配，只要出现 dynamic_batching 就直接退出（scripts/lib/manifest.py:237-238）。理由写在运维注意里——「不要启用 dynamic_batching，除非重新导出并验证带 batch 维度的 ONNX」（docs/deployment.md:888）。

        因果是闭合的：ONNX 是按固定 shape 导出的，第一维写死成 1，攒批需要的那个可变批维根本不存在。打开开关不会换来吞吐，只会换来形状对不上。

        请把这两层分开记：在 Triton 那一层，这是一个合法开关；在这个仓库这一层，它是一条会让 CI 直接失败的红线。换一个模型仓库，红线不一定还在，但 Triton 的语义不会变。全文往后还会遇到几次这种叠加，每次都该问一句「这条到底是谁定的」。

        一段 JSON 字符串也可以是模型的对外接口

        pipeline 那份配置的输入输出都是 TYPE_STRING、dims: [ 1 ]——一个元素的字符串张量。它没有把音频地址、输出格式、限额这些业务参数各做成一个 tensor，而是整包塞进一段 JSON。代价是 Triton 帮不上忙：它不知道这段字符串里有什么，形状校验只能校验到「是一个字符串」为止，JSON 里少了个 key 只能由 model.py 自己发现并报错。换来的是业务契约可以独立演化，加一个字段不必改 config.pbtxt、不必重新过一遍模型加载。这也解释了为什么后面几站讲请求体时，谈的全是 JSON 的字段，而不是 tensor 的维度。

        instance_group：只给依据，不给数

        五个模型都写 count: 1、kind: KIND_GPU。count 是这个模型在设备上起几个执行实例，文档给出的唯一依据是「instance_group.count 会增加内存或 GPU 显存占用」（docs/deployment.md:889）。要不要往上调，取决于四个 ONNX session 各占多少显存、卡上还剩多少——这两个数仓库里一个都没有。第 06 站会说明「没有实测数据」在这条链路上是常态，以及该怎么自己补上。

        本站收束config.pbtxt 决定了 Triton 用哪条路径装载模型、认哪种形状，以及这个仓库额外画了哪几条红线。但它管不到模型目录从哪来、容器用什么镜像、/models 由谁挂上去——那是下一站那份部署 JSON 的职责。
        [ 05 · 部署 ]

        一份 EAS JSON：逐字段拆，包括三个答不上来的字段

        上一站的所有 config.pbtxt 都住在 /models 里，而 /models 在容器里只是一个挂载点。谁把 OSS 上的 release 目录挂到这个路径、用哪个镜像、开哪个端口、服务叫什么名字，全都不在模型仓库里，而在一份提交给 PAI-EAS 的 JSON 中。这份 JSON 不到 30 行，坑却几乎集中在其中三四个字段上——另外还有三个字段，这个仓库回答不了。

        线上实际使用的部署 JSON，逐行可点。右侧（窄屏为下方）展示这个字段控制什么、写错会怎样、依据在仓库的哪里。带「未知」标记的三行是仓库里查不到任何依据的字段，本文不给它们编解释。

        最容易踩的一条：oss.path 指的是 model repository 的根

        storage[0].oss.path 挂到 mount_path: /models，而启动命令是 tritonserver --model-repository=/models。三者串起来的含义是：oss.path 下面紧接着一层就必须是模型目录本身，不能再套一层。这条写错时的症状很有欺骗性——服务能起来，容器不报错，只是一个模型都不 ready。运维文档把它列在「模型没有进入 READY」的第一条排查项：先确认填的是 release 根目录，而不是某个单模型目录。

        换 release 只动一个字段

        镜像、依赖、挂载点、启动命令、端口都与模型内容无关，所以发布一个新版本的模型仓库，改的只有 oss.path 里的 release 名。回退也一样：把路径指回上一个 release。这正是「模型仓库是一个目录」这件事带来的好处——发布物是不可变的，切换发布物不需要重新构建任何东西。

        启动命令为什么只有一个参数

        script 里只有 tritonserver --model-repository=/models，没有指定 backend、没有指定版本策略、没有列出要加载哪些模型。这不是省略，是分工：该由命令行决定的事在这条链路上都不由命令行决定——用哪条装载路径、张量什么形状、起几个实例，写在各模型的 config.pbtxt 里；加载哪些模型、哪个版本，由 /models 的目录结构决定。上一站那份契约存在的意义，在这一行命令的短小上体现得最清楚。

        端口这边则有一处不对称：Triton 容器默认同时发布 HTTP 8000、gRPC 8001 和 metrics 8002（docs/deployment.md:278-280），而这份 JSON 只声明了 port: 8000。也就是说 gRPC 和 metrics 这两个口在这次部署里没有被声明出去——服务本身照常工作，但凡是要走这两个口的用法，都不能默认它们在。

        三处必须承认不知道

        env 里的 {"name": "oss", "value": "4"}：整个仓库一次都没出现过这个环境变量，渲染脚本也从不生成 env（scripts/lib/pai_eas_config.py 构造的 container 只有 command、image、port、可选的 prepare）。它是什么意思，只能查阿里云 PAI-EAS 的官方文档或者问平台侧。本文不猜。

        labels 里的 $SYSTEM_SERVICE_DEPLOY_TYPE: "triton"：同样零命中，渲染脚本也不生成 labels。看名字像是平台侧的部署类型标记，但「像是」不等于知道。本文同样不猜。

        readOnly: false：全仓库只在另一条线（ASD）的部署配置里出现过一次，且没有任何解释文字。反差是明确的——本地 Docker 那条路径是显式只读挂载的（scripts/triton.sh:237 用 -v …:/models:ro），release 目录被文档当作不可变发布物，推理过程中真正要落盘的中间文件也都写在进程自己创建的临时目录里，不写 /models。按这些线索看，/models 不需要可写。但「不需要可写」推不出「这次为什么设成了 false」，仓库里没有依据。要么实测把它改回只读跑一遍，要么问平台侧这个字段在 EAS 上的默认行为，不要凭反差就断言它错了。

        仓库里那份同名 JSON 不是线上真值

        仓库里确实有一份 eas/configs/triton-service.json，但它是渲染脚本的模板产物：服务名是默认值，oss.path 指向另一个 release，用的键是 command 而不是 script，机型写成 instance_type 字符串加 instances: null，并且完全没有 env、labels、readOnly。它还多挂了一个 /dev/shm 的内存盘，多带一段 prepare.pythonRequirements。把它当成「线上配置的副本」去对照，只会得出一堆假差异。仓库里的模板回答的是「脚本会生成什么」，不是「线上跑的是什么」。

        本站收束这份 JSON 决定了容器长什么样、/models 从哪来、服务叫什么名字。提交之后到控制台显示「运行中」之间，容器里还有一段没人看得见的过程——下一站把它拆成阶段，并说清哪些阶段仓库里连一个实测数字都没有。
        [ 06 · 冷启动 ]

        从容器被拉起，到 Started HTTPService

        JSON 提交上去，控制台上的状态会从「部署中」变成「运行中」。这中间容器里发生了什么，只有日志知道。这一站按文档能支撑的顺序把这段过程拆成六个阶段，给出每个阶段的日志特征，并且明确标出：耗时那一栏，整个仓库一个实测数字都没有。

        冷启动阶段条，每格可点。六格等宽只表示先后顺序，不表示耗时占比——按比例画就必须有实测数据，而这份数据不存在，见下方说明。

        并行加载，和一个没有被解释的参数

        第 4 阶段里，Triton 扫完一级目录之后是并行加载模型的：几个 ONNX session 与 Python backend 的解释器进程会同时往上起。仓库另一条线的部署脚本显式加过 --model-load-thread-count=1 把它改成串行，但文档里没有写为什么——是撞过显存峰值，还是撞过依赖竞争，配置本身不说话，本文也不替它编一个原因。知道有这么个开关、知道它在这个仓库里被用过一次，就够了；真要用它，得先有能支撑判断的观测。

        还有一处顺序上的因果：模型状态表打印在所有加载动作结束之后，而 HTTP 端口开在状态表之后。所以「表已经打出来了但端口还没开」是一段真实存在的窗口期，而且这段时间里所有请求得到的都是连接层面的失败，不是任何一种业务返回码。

        为什么必须看日志，而不是只看返回码

        就绪探针在「模型还在加载」和「模型加载失败」这两种情况下的返回码是同一个，都不是 200。这两件事的处理方式完全相反：前者只需要再等，后者再等一万年也不会好。返回码本身分不开它们，能分开的只有日志——看有没有对应模型的 successfully loaded，以及有没有 ONNX Runtime、Python backend、CUDA、显存或文件权限的报错。

        这就是全文那个主问题的第一个注脚：一个状态码承载的信息量，比它看起来少。探针本身有几层、每层的 200 各自证明了什么，是第 07 站的事。

        没有实测耗时，就不要有实测耗时

        OSS 首次挂载要多久、 个各 （合计 ）的 ONNX 首读要多久、ONNX Runtime 建 session 要多久、Python backend 起解释器要多久、pip install 要多久——这五个数字在整个仓库的文档里一个都没有。本文不编。

        要拿到它们不难，也不需要额外工具：在 PAI-EAS 控制台的服务日志里打开时间戳，找到 行 successfully loaded（本 release 下每个模型一行）和那一行 Started HTTPService，读它们之间以及它们与容器启动之间的间隔。跑几次冷启动取一组数，这个服务的冷启动画像就有了，而且是你自己这块卡、这个地域、这个 release 的真实数字，比任何转述都可靠。

        顺序里有一条容易被忽略的成本

        prepare.pythonRequirements 执行的是普通的 pip install，也就是说这些包不在镜像里，而是每次容器启动都要联网重新装一遍。这一步失败或超时，后面的 Triton 根本不会启动，日志会停在装包输出上，模型状态表一行都不会出现。这一站给出的六阶段是通用顺序，第 05 站那份 htdemucs 的 JSON 里没有 prepare，所以第 2 阶段对它是空的；仓库里那份渲染模板则带着三个包。判断你的服务卡在哪，先确认自己这份配置里第 2、3 两个阶段到底存不存在。这件事的实际影响不只是慢：一个每次启动都要联网装包的服务，它的冷启动时间与外部网络绑定，扩容、重启、故障恢复都会受它牵连，而这一切在服务跑起来之后的任何指标里都看不见。

        本站收束冷启动的终点是日志里那行 Started HTTPService at 0.0.0.0:8000——在它之前，端口还没开；在它之后，才谈得上有没有拿到状态码。而拿到 200 只是下一个问题的开始：这个 200 到底是谁在回答，它证明的是「进程活着」还是「模型能推」。第 07 站从这里接。
        [ 07 · 就绪 ]

        六层 ready，各自证明了什么

        上一站的结论有点难受：容器起没起来只能靠日志里的特征行判断，「还在加载」和「某个模型加载失败」在返回码上分不开。现在假设你终于等到了 /v2/health/ready 返回 200。这个 200 到底买到了什么？答案是：比你以为的少得多。「服务能用」不是一个结论，是六个互相独立的结论叠起来的，每一层只封住一类失败。

        先把三个名字分开

        htdemucs_test 是 PAI-EAS 的服务名——就是 05 站那份部署 JSON 里的 metadata.name。它出现在公网 endpoint 的路径里，/api/predict/htdemucs_test 这一段属于 EAS 网关的路由，跟容器里装了哪些模型没有任何关系。Triton 的模型名是另一套：audio_stem_separation_pipeline 和四个 htdemucs_ft_*，它们来自模型仓库的目录名与 config.pbtxt 里的 name（见 04 · 契约）。两套名字在同一条 URL 上前后相邻，这就是它们容易被拌在一起的原因。

        http://<id>.ap-southeast-1.pai-eas.aliyuncs.com/api/predict/audio_stem_separation_triton①/v2/models/audio_stem_separation_pipeline②/versions/1/ready

        • ① 点线 PAI-EAS 服务名，网关路由用；改它等于换一个服务。
        • ② 实线 Triton 模型名，Triton 内部查表用；改它等于换一个模型。

        同一条 URL 上两段名字，归属两个完全不同的系统。这是文本标注图，不是抓包结果。

        把服务名填到模型名的位置上去查 ready，拿到的是这么一行：

        {"error":"Model version not ready"}

        这句话极具误导性。它读起来像「模型还没加载完，再等等」，实际含义是「叫这个名字的模型根本不存在」——等下去不会变好，重启也不会变好。仓库的验收 runbook 专门为这个坑留了一句话：看到这个报错不要直接判断服务异常，先确认你是不是把 PAI-EAS 服务名误当成了 Triton 模型名。

        分层探针梯子

        下面这把梯子把「服务能用」拆成六格。选中某一层，它和它下面的层被点亮成已证明，上面的层仍然是未证明——这正是每次验收时你手里真实的信息量。每层给出完整命令、期望响应，以及这一层坏掉时最典型的样子。

        探针梯子：点某一层，看它证明了什么、还剩什么没被证明。命令中的 EAS_BASE / EAS_TOKEN 见下方「命令形式」。页面不联网，所有响应都是文档记载的期望形态，不是本次运行的真实输出。

        runbook 把三类探针的分工写成了三句话，原样记住：

        ready 检查的是「模型是否加载」
        metadata 检查的是「调用方应该怎么传 tensor」
        infer 检查的是「这份 tensor 是否真的能完成推理」

        前两句都不碰 GPU。只有第三句会真的把数据推进计算图里。

        命令形式：三个会让人卡住的细节

        鉴权头是裸 Token。头名是 Authorization，值就是 PAI-EAS 的 Token 本身，前面不加 Bearer。加了会被判为无效凭证。

        base 不带 scheme。仓库里 EAS_BASE 的形态是 <id>.<region>.pai-eas.aliyuncs.com/api/predict/<服务名>，已经含到服务名为止；/v2/... 直接拼在它后面，scheme 由调用方在外面补。tritonclient 的 url= 同样要求不带 scheme。

        ready 成功时 body 为空。所以 curl 什么都不打印是正常现象，不是请求没发出去。要看结果必须打状态码：-o /dev/null -w '%{http_code}\n'。文档为这一条专门开过一节问答。

        查漏补缺：照抄仓库那份验收 runbook 会失败。它的 TRITON_MODELS 列了九个模型（四个 htdemucs_ft_* 加五个 ASD 相关模型），判据也写成「九个 /v2/models/<model>/versions/1/ready == 200」。而本次 release 的模型仓库里只有五个模型，照抄会在第五个模型上拿到非 200 而中止，看起来像「服务坏了」，实际是在查一个这次根本没部署的模型。

        更要命的是那份清单里恰好漏了 audio_stem_separation_pipeline——这次唯一的业务入口模型。也就是说，照着 runbook 全绿跑完，你验的仍然全是 expert，一次都没碰过真正对外的那个模型。本次正确的五个模型是：

        一处诚实标注。/v2/health/live 与 /v2/health/ready 的语义差别，这个仓库的文档没有写：两个脚本里一个查两个端点、一个只查 ready，谁也没解释为什么。上面梯子里 L0 与 L1 的分工来自 KServe v2 推理协议的标准约定（live 表示进程存活，ready 表示可以接请求），属于协议常识，不是本仓库文档的说法。真要较真，应以所用 Triton 版本的协议实现为准。

        本站收束六层里前四层都能用 curl 走完，第五层 L4 走不动了：它要求你真的把一个张量送进 GPU。下一站就造这个张量——一个 [1, 2, 343980] 的零张量，是「这个服务真的能算」这句话最短的证据。
        [ 08 · 探针 ]

        最小可验证例子：一个零张量

        梯子在 L4 断开的原因很实在：前四层问的都是「你怎么说」，L4 问的是「你算一个给我看」。而要让服务真的算一次，最短的输入不是一段音频，是一整块零——形状 [1, 2, 343980] 的 FP32 张量，喂给任意一个 htdemucs_ft_*。它分离不出任何东西，但它能证明的东西比你想的多。

        为什么一块零就够

        这一步不检验分离质量，它检验的是「能不能算」这条链上的每一环：模型文件被容器读到了、ONNX Runtime 的 session 建起来了、GPU 上下文可用、请求里的输入名 mix 和输出名 stems 与 config.pbtxt 对得上、返回的 shape 与 dims 一致。这些环节里任何一个断了，返回的都不会是「一个内容不对的结果」，而是一个错误——所以内容全零完全不影响判据。至于 343980 这个数从哪来、为什么恰好是 7.8 秒，见 11 · 切段；这里只把它当成 config.pbtxt 已经写死的合同形状来用。

        探针构造器：选一个 expert，看这一步要构造什么张量、要在网络上搬多少字节、期望打印哪一行，以及它证明了什么、没证明什么。下面全部是构造与期望，不是真实推理输出——本页不联网，也没有模型。

        为什么不能用裸 curl

        体积算一下就明白了。输入 1 × 2 × 343980 个 FP32 数，输出 1 × 4 × 2 × 343980 个——一次 smoke 的往返数据量在下图里按形状直接算出来。要用 curl 走 KServe 的 JSON 形态，就得把这些浮点数逐个写成文本数组塞进 data 字段，手写不现实，脚本生成也会把体积再放大好几倍。所以真实 infer 这一步走 tritonclient[http]：它用二进制张量扩展传数据，客户端只需要 python3 -m pip install 'tritonclient[http]' numpy。

        scripts/pai-eas-triton-check.sh · --infer 内嵌的 Python（建连、infer helper、smoke_htdemucs 三段拼在一起，中间省略无关代码）

        高亮的五行就是这一步的全部实质：鉴权头在每次 client.infer(headers=...) 上带、不在建连时带；造零张量；按名字包成 InferInput；请求指定名字的输出；拿回来先校验 dtype 再比 shape。connection_timeout 与 network_timeout 共用同一个 --infer-timeout 值。

        超时与节奏

        脚本的 --infer-timeout 默认就是 300 秒，同时用作 connection_timeout 和 network_timeout。runbook 给的理由原文是：「新加坡 EAS 上 htdemucs 推理可能超过默认 60 秒，建议 300」。请把这句读成配置建议，不是实测耗时——它说的是「默认 60 秒可能不够」，没有给出任何一次真实推理的时长，本文也不替它编一个。

        另一条节奏上的约定同样是文档明写的：逐个模型跑，不要串起来跑。runbook 把四个 expert 拆成四条命令，一行一个，理由写在上一行——避免多个模型连续推理被单个慢请求拖到网关超时。串着跑的坏处不只是慢，是失败时你分不清是哪个模型的问题，还是网关在总时长上把整批掐了。

        如果 L0–L3 全是 200、偏偏这一步失败，问题已经不在「能不能连上」，而在这次推理请求本身。runbook 给的归因方向有五条：

        • 输入名或输出名与该模型的 metadata / config.pbtxt 不一致；
        • 输入 shape 或 dtype 与合同不一致；
        • Python backend 模型的权重、运行时代码或部署层依赖有问题；
        • PAI-EAS 网关或服务侧限制了请求体大小——按上面算出的往返体积，这条完全先查；
        • 模型推理阶段自己报错，这时只能去看 EAS 日志。

        一条硬边界：--infer 不支持 audio_stem_separation_pipeline。检查脚本的 validate_infer_model 是一张白名单，里面只有四个 htdemucs_ft_* 和几个 ASD 模型；传 pipeline 进去会被参数校验直接拒掉，连请求都发不出。

        所以「四个 expert 都 infer 通过」不等于 pipeline 通过。中间还隔着一整段跟 GPU 无关的东西：从 OSS 把输入拿下来、把结果写回去。expert 全绿而 pipeline 失败，是完全可能、而且相当常见的组合。

        覆盖最全的那条链：六步诊断

        pipeline 的真实 infer 只能走另一条路——由 scripts/oss/pipeline_command.py 生成、在 Triton 那台机器上执行的诊断脚本。它把验收拆成六步：

        [1/6] health live + ready，再逐个查 5 个模型的 /v2/models/<model>/ready
[2/6] 拉 5 份 /v2/models/<model>/config，校验 request envelope 与配置契约
[3/6] 从 Triton 这台机器上对输入对象做 signed GET range 探针（只拉 1 字节）
[4/6] POST /v2/models/audio_stem_separation_pipeline/versions/1/infer
[5/6] 解析 response_json，校验输出契约
[6/6] done

        第 3 步单独说一句。它做的事只有一件：

        curl -fsS -r 0-0 -o /dev/null "$(cat "$DIAG_DIR/input-url.txt")"

        -r 0-0 只要第一个字节，-o /dev/null 连存都不存。它不关心音频内容，只回答一个问题：Triton 这台机器，能不能凭这个签名 URL 读到输入对象。有了这一步，「pipeline 失败」就被劈成了两半——探针失败说明是网络、签名、过期或权限，跟模型完全无关；探针通过而第 4 步失败，才轮到怀疑模型和编排。把不可控的外部依赖单独探一次，是这套脚本里最值钱的一个设计。

        本站收束零张量证明了「能算」，签名探针证明了「读得到」。剩下最后一个问题：第 4 步那个 request.json 里到底写了什么，pipeline 又凭什么把一条请求当场拒掉。
        [ 09 · 请求契约 ]

        一条请求长什么样，以及它怎么被拒

        pipeline 对外只有一个输入：request_json，TYPE_STRING，dims: [1]。一个字符串。这意味着 Triton 这一层根本不知道你在传什么业务参数——它只负责把一串字节交给 Python backend。整份业务契约都装在那个字符串里，这是 04 · 契约 那个 TYPE_STRING [1] 的直接后果，也是这一站要走读的全部内容。

        信封与内容

        发给 Triton 的 HTTP body 长这样，它只是个信封：

        {"inputs":[{"name":"request_json","shape":[1],"datatype":"BYTES","data":["<json string>"]}],
 "outputs":[{"name":"response_json"}]}

        信封上没有 run_id，没有音频地址，没有任何一个业务字段。Triton 校验的只有名字、shape 和 datatype 三件事；data[0] 里那串东西对它而言就是不透明的字节。换句话说，Triton 层的「合法」和业务上的「合法」是两回事：信封填对了照样可以被里面的内容拒掉，而且必须由 Python backend 自己去拒。

        下载与解码：为什么这么挑剔

        请求已经通过校验，OSS 上那段音频也已经落到容器的临时目录里，叫 input.wav。但这时它还只是一串字节。把字节变成模型能吃的数组是 _decode_wav() 这二十几行干的事——注意，它一路都在拒绝，而不是一路都在适配。

        models/htdemucs/audio_stem_separation_pipeline/1/model.py · _decode_wav()

        第 2 行就定了调子：用 Python 标准库的 wave 打开一个内存里的字节流，不引入 ffmpeg，也不引入 soundfile。代价是只认 PCM 编码的 WAV，换来的是这个 Python backend 的依赖树里少了一整条音频解码链——容器镜像更小、冷启动时要加载的东西更少。这是一次明确的取舍，不是偷懒。

        接下来两个 raise 是这一站的性格所在。sample_rate != SAMPLE_RATE 直接报错，而不是就地重采样：模型是在 44100 Hz 上训练的，后面那个写死的段长 343980 也是按 44100 折算出来的秒数，采样率一变，段长代表的时间长度就跟着变，模型看到的东西不再是它训练时见过的东西。服务端如果偷偷帮你重采样一次，出来的结果会「能听」但没人说得清偏差从哪来。所以责任被推回上游：谁调用谁负责喂 44100 Hz。声道数同理，模型输入形状的第二维写死是 2，非立体声连形状都对不上，早退出比晚崩溃便宜。

        位深这一段是真正的解码。16-bit PCM 按小端有符号整数读出来除以 32768.0，32-bit 除以 2147483648.0，都归一化到 [-1, 1] 的 float32；除数取的是该位宽的负半轴满量程，所以结果落在 [-1, 1) 而不会溢出。除此之外的位宽——8-bit、24-bit——一律拒收。

        交错存储是什么

        立体声 WAV 的数据块里，左右声道不是分成两段各存一半，而是按帧交替写：L0 R0 L1 R1 L2 R2……一帧就是同一时刻两个声道的一对采样点。这样存的好处是播放器顺序读一遍就能同时拿到两个声道，坏处是同一个声道的相邻采样点在内存里并不相邻，中间永远隔着另一个声道的一个数。

        而模型要的是相反的排布：先一整条左声道，再一整条右声道，即 (2, samples)。所以解码的最后一步一定有一次重排。

        图：6 帧立体声的排布变化，格子里的数值是用固定种子生成的示意值，不是真实音频采样，也不是任何模型的输出。要看的是形状与底层缓冲区顺序怎么随三次操作变化，不是数值本身。

        data.reshape(-1, channels) 把一维的 12 个数看成 (6, 2)，这一步只改解释方式，一个字节都没搬。data.T 转成 (2, 6)，形状对了，但转置在 NumPy 里同样不搬数据，它只是把 strides 反过来——底层缓冲区仍然是 L0 R0 L1 R1 的交错顺序。np.ascontiguousarray 才真正申请一块新内存，按 C 顺序把数据抄成 L L L L L L R R R R R R。

        这一次拷贝不是可有可无的洁癖。后面每一段都要做 mix[:, start:end] 这样的切片，再打包成 Triton 的输入张量交给 ONNX；张量要的是一段连续的、按行优先排好的缓冲区。如果留着非连续的转置视图，这次拷贝也只是被推迟到后面每段各做一次，而不是在这里一次做完。

        最后一件事的顺序：时长上限 limits.max_duration_seconds 的校验不在校验函数里，而在解码之后。

        同一文件 · _run_pipeline() 中调用解码的那几行

        原因很直白：WAV 头里的字段可以对不上实际数据，真实时长要等 mix.shape[1] / sample_rate 算出来才算数。字节数上限能在下载时就卡住（max_input_bytes 传给了下载函数），时长上限卡不住，只能先把整段解出来再回头判。这意味着一个超长输入仍然会占用一次完整解码的内存和时间，然后才被拒绝。

        这一站会抛的错，以及触发条件
        • wave.Error（标准库抛的，不是本函数的 raise）：字节流不是合法的 RIFF/WAVE，或不是 PCM 编码——MP3、FLAC、IEEE float 编码的 WAV 都停在 wave.open() 这一行。
        • RuntimeError: audio input must be 44100Hz：采样率不是 44100。
        • RuntimeError: audio input must be stereo：声道数不是 2，单声道也不行。
        • RuntimeError: audio input WAV must use 16-bit or 32-bit PCM：sample_width 不是 2 或 4，8-bit 与 24-bit 落在这里。
        • RuntimeError: input audio exceeds configured duration limit：解码后算出的时长超过 limits.max_duration_seconds。

        这些异常都会被 execute() 外层的 try 接住，写进 response_json 的 error 字段返回，而不是让请求本身失败。

        [ 11 · 切段 ]

        343980 从哪来，一首歌被切成几段

        上一站交出来的 (2, N) 里，N 是整首歌的采样点数。而 ONNX 模型的输入形状是固定的 [1, 2, 343980]——不是「最多 343980」，是「必须正好 343980」。全文后面所有的数字，都是从这一个常量推出来的。

        四个 config.pbtxt 里，输入 mix 的 dims 写的是 [ 1, 2, 343980 ]，输出 stems 是 [ 1, 4, 2, 343980 ]，两个都没有动态轴。这不是配置写得死板，而是导出 ONNX 的那一刻就把段长冻进图里了：形状固定的图，运行时不必等第一次请求进来才知道每一层的中间缓冲该开多大。代价就是服务端从此只接受这一个长度。

        于是任意长度的音频都必须被切成 7.8 秒一段，一段一段地喂。切法写在 _separate() 的开头和 _segment_ranges() 里，一共不到十行。

        model.py · _separate() 开头与 _segment_ranges()

        先看 overlap 和 stride：OVERLAP_RATIO = 0.25，取整后每段与下一段重叠四分之一段长，剩下的四分之三是窗口每次前进的距离。所以段与段之间不是首尾相接，而是彼此咬住一截。

        为什么要咬住？因为模型在处理一段音频时，判断某个瞬间该归到哪一轨，靠的是这个瞬间前后的一片上下文。段的正中间上下文最全，越靠近边界越残缺——边界之外的声音根本没进这一次输入。如果直接首尾相接，两段各自残缺的边界正好拼在一起，接缝处就会听到音色突变或者一声「咔」。重叠的意思是：让每一个靠近边界的采样点，在相邻那一段里同时也是一个靠近中间的采样点，于是同一段时间有两份质量不同的结果可选。怎么把这两份合成一份，是下一站的事，这里只需要知道重叠是为此存在的。

        「边界缺上下文」具体缺的是什么

        把一段音乐里的人声抠出来，不能只看单个采样点的数值——同一个瞬时电平既可能来自人声也可能来自贝斯。模型要看一小片时间窗内的频谱走向、起音形状、周期性，才能判断这一小片属于谁。

        段的第一个采样点前面什么都没有，最后一个采样点后面什么都没有，模型在这两处只能拿单侧的上下文做判断。这跟窗函数、淡入淡出无关，是输入本身就少了一半信息。

        段数是怎么算出来的

        核心是这一行：segment_count = 1 + max(0, (total_len - segment_samples + stride - 1) // stride)。拆开看，total_len - segment_samples 是第一段放好之后，还剩多少采样点没被覆盖；这些剩余量要按 stride 一步一步往前挪来覆盖，需要挪的步数是「剩余量除以 stride 向上取整」。而 (a + b - 1) // b 正是整数向上取整的标准写法——不引入浮点，也就不会出现 math.ceil 在临界值上因浮点误差多算一步。max(0, …) 处理音频短于一段的情形：此时括号里是负数，步数归零，只切一段。最后 + 1 加回第一段本身。

        每段的区间是 (index * stride, min(index * stride + segment_samples, total_len))。最后一段的右端被 min 截到音频结尾，于是它往往短于 343980；而模型不接受更短的输入，所以循环里紧接着一句 np.pad 把它右侧补零到整段长。补出来的那截静音也会被模型算一遍，只是拼回去时落在音频长度之外，不会进最终结果。

        [ 12 · 子推理 ]

        四个模型，每个只认自己那一行

        上一站结束时手里有一段 [1, 2, 343980] 的输入张量。按直觉，把它送进「那个 htdemucs 模型」跑一次就该拿到四轨。实际发生的是：它被送进四个模型各跑一次，每次都拿回完整的四轨，然后每次只留一行。

        原因在模型本身。htdemucs_ft 里的 ft 是 fine-tuned——它不是一个模型，而是四个：htdemucs_ft_drums、htdemucs_ft_bass、htdemucs_ft_other、htdemucs_ft_vocals，各自针对一种音轨额外微调过。四个 config.pbtxt 里输入输出的形状一字不差，每一个的输出都是 [1, 4, 2, 343980]：四条轨、两个声道、一段的长度。也就是说，人声模型照样会输出一份鼓、一份贝斯、一份其它，只不过那三份不是它被调好的方向。

        仓库里用 pipeline_config.json 把「谁负责第几行」显式写死，一个模型一个 target_row：

        stemnameversiontarget_row这一行的含义
        四轨的顺序为什么是 drums / bass / other / vocals

        这个顺序不是代码作者定的，是 htdemucs 模型自身输出通道的固有顺序，导出成 ONNX 之后就体现为 stems 张量第二维的下标。other 是「除了鼓、贝斯、人声之外剩下的一切」——吉他、键盘、弦乐、合成器都在里面。

        代码没有去猜这个顺序，而是把它抄进 pipeline_config.json 的 target_row，启动时由 _validate_specs 检查这四个数排序后必须正好是 0、1、2、3。写错一个，服务在初始化阶段就起不来，而不是安静地输出错轨。

        audio_stem_pipeline/htdemucs.py · TritonHtdemucsBackend.infer()

        这段就是 BLS（Business Logic Scripting）：在一个 Python backend 模型内部，构造 pb_utils.InferenceRequest 指名另一个模型，调 .exec() 同步拿结果。它不是 HTTP 请求，不经过网络栈，也不用再走一遍 Triton 的 HTTP/gRPC 前端——省掉的是一次序列化与一次网络往返。但目标模型自己的调度照走：四个 ONNX 模型在 config.pbtxt 里声明的 instance_group 依然生效，它们 stats 里的 queue 也会记上这一次。这正是 15 站那条排队判定能用在这四个模型上的前提。而客户端从头到尾只发了一次请求。

        preferred_memory=PreferredMemory(TRITONSERVER_MEMORY_CPU, 0) 这一句是在说：把输出张量放回 CPU 内存的第 0 个 device 上。ONNX 模型的 instance_group 是 KIND_GPU，输出本来在显存里；仓库没有说明为什么加这一句，下面是对 PreferredMemory 语义的推断、不是实测结论：不加它，Python 侧拿到的可能是一个 GPU 张量，而后面 output[stem][:, start:end] += … 是 NumPy 运算，只能在主机内存上做。加上它，代价被摆到明处：每一次子推理的整个输出张量都要从显存拷回主机内存，包括那三行马上就要被丢掉的。

        model.py · _separate() 的内层循环

        取行就是 raw[0, result.target_row, :, :chunk_len] 这一下：批维取 0，第二维取自己的 target_row，声道全取，时间维只取到 chunk_len——最后一段补零补出来的尾巴在这里被切掉。行末那个 * chunk_window 与随后的权重归一化属于下一站，这里先不看。取行之前那两句形状与 dtype 的检查也要看：raw.shape != (1, 4, CHANNELS, SEGMENT_SAMPLES) 就直接报错，不试图 reshape、不试图截断——形状对不上说明部署的 ONNX 不是这一版，继续算只会算出垃圾。

        丢弃 3/4 的代价，具体是多少

        这不是实现失误，是选 htdemucs_ft 而不是基础版 htdemucs 的直接后果：基础版一个模型跑一次出四轨，微调版四个模型各跑一次、各取一轨。多花的算力换的是每一轨都由专门微调过的权重给出。这个交换划不划算取决于场景，但代价可以精确算出来——下面这些数全部由页面上的常量当场推出。

        取行矩阵：行是四个模型，列是它们输出张量的四条轨。用方向键在格子间移动，回车或点击查看这一格对应的形状与体积。对角线是「采用」，其余 12 格是「丢弃」——注意每一格都真的被算出来过，也真的从显存拷回过主机内存。这里的形状与字节数是按常量实算的，不是实测的运行数据。

        为什么这一层不能是 ensemble

        Triton 自带 ensemble，可以在配置里声明「A 的输出接 B 的输入」，不写一行 Python。这里用不了，原因不在模型而在循环：段数取决于输入长度，是运行时才知道的；每一段的四次子推理结果要按各自的偏移累加进同一块 (2, total_len) 的输出缓冲，还要同时维护一个权重数组。ensemble 描述的是一张静态的数据流图，节点和连边在加载时就固定，它表达不了「循环 N 次、N 由输入决定、每次都往同一块可变缓冲里累加」。需要状态和控制流的地方，就得有一个真的解释器在跑——这就是 Python backend 在这套模型仓库里存在的理由。

        本站收束循环跑完，四个 stem 各自有了一块 (2, total_len) 的缓冲，里面装的是所有段加权累加后的和。但「和」还不是答案：重叠区被加了两次，权重也还挂在上面。把它除回去，才是下一站要做的事。

        接缝是怎么消掉的

        上一站跑完，内存里躺着的是一堆段：每一段 7.8 秒、两个声道、四个 stem 各一份 float32 估计。它们不是首尾相接的，相邻两段在时间轴上重叠 1.95 秒（见 11 · 切段），也就是说同一个时刻会有两份互不相同的估计等着被处理。这一站只解决一件事：把这些带重叠的段还原成一条听不出拼接痕迹的整轨。

        先看不重叠会怎样

        假设段与段真的首尾相接。模型在段边缘拿到的上下文是残缺的——段首之前的声音、段尾之后的声音它都没见过，而分离一个音符的起始和衰减恰恰要靠前后文。于是同一个时刻，落在前一段尾巴上的估计和落在后一段开头的估计不会相等：可能是一点低频漂移，可能是一点没扣干净的残留。两段硬接起来，波形上就出现一个不连续点，听感上是每隔一个 stride 一次的「咔」。这个错误不会随着模型变强而消失，因为它根本不是模型算错了，而是两个正确答案被强行拼在了一起。

        解法是让相邻段重叠一段，在重叠区做加权平均：前一段的权重从 1 线性降到 0，后一段的权重从 0 线性升到 1。估计的差异不再是一个跳变，而是被摊平在 1.95 秒里的一次平滑过渡。

        窗长什么样

        _make_transition_window 造的就是这条权重曲线：一个和段等长的一维数组，两端各一段 np.linspace(0, 1) 的线性斜坡，中间恒为 1。斜坡的长度就是 overlap，由 segment_samples × overlap_ratio 取整得到。

        _chunk_window 再按段的位置改一改：第一段的开头、最后一段的结尾都没有邻居，那一侧的斜坡被强行拉平成 1.0；最后一段还可能被音频总长截短，所以先按 chunk_len 切一刀。三种形态并排放在一起是这样的：

        为什么最后要除以 weight

        累加这一步在 _separate 的循环里只有两行：每个 stem 把自己那一行的估计乘上 chunk_window 加进整轨缓冲，同时把同一条 chunk_window 加进一条共用的 weight。循环结束后再逐样本相除。

        纯线性窗在重叠区相加恰好等于 1：重叠区第 k 个样本上，后一段的窗值是 k / (t − 1)，前一段在同一位置的窗值是 (t − 1 − k) / (t − 1)，两者之和与 k 无关。所以如果每一段都用未经修改的原窗，除法就是一次恒等操作。

        问题出在被改过的那些段。末段的尾部被 result[-edge:] = 1.0 拉平，如果这条末段又足够短，被拉平的区间会正好压在前一段的淡出斜坡上——两条曲线一个恒为 1、一个从 1 降到 0，加起来会明显超过 1。把实验台的演示时长切到 20 秒就能看见这个包：权重最大值实算是 1.7436。不除以 weight，这段结尾就会响出 +4.83 dB 的鼓包。

        np.maximum(weight, 1e-8) 防的是除零。在当前这套常量下，weight 落到 0 只有一个现实来源：假如 _chunk_window 不做首尾拉平，第 0 号样本上原窗的值恰好是 linspace(0, 1) 的那个 0，而这个位置只有第一段覆盖得到，weight 就是货真价实的 0；末段刚好满长时，最后一个样本同理。拉平之后这两个奇点消失，1e-8 变成一道空转的闸——它守的是以后有人改常量（比如把 stride 调到大于 segment，让中间出现没被任何段覆盖的样本）。

        另一个不能取 overlap_ratio = 0 的理由藏在写法里：window[-transition:] 在 transition == 0 时等价于 window[0:]，即整条数组，赋一个空数组进去会直接抛 ValueError。_chunk_window 里的 result[-edge:] = 1.0 在 edge == 0 时同样会把整条窗刷成 1。这是当前实现的行为，不是它一定错，但它决定了这两个参数不能随手清零。

        这些缓冲要占多少内存

        累加需要先把四条整轨的空缓冲开出来：{stem: np.zeros((2, total_len), float32)}，外加一条长度为 total_len 的 weight。它和段数无关，只和音频总长有关，而且从第一段开始就得一直占着。

        四轨变两轨，再变成两个文件

        重叠相加交出来的是四条整轨：drums、bass、other、vocals，每条都是 (2, total_len) 的 float32。但这个接口对外只承诺两个对象——一条人声、一条伴奏。从四条到两条、从 float32 到 WAV 字节、从进程内存到 OSS 上的一个 key，这三跳每一跳都有它自己的取舍。

        三条相加，中间不做任何归一

        伴奏就是 drums、bass、other 三条直接相加，没有除以 3，没有峰值归一，也没有任何限幅。这在数学上是对的：如果四条 stem 是对原混音的一个精确分解，那么三条之和加上 vocals 就应该等于原混音，各自的幅度本来就该原样保留。但第 12 站已经说清楚，这四条是四个独立模型各估各的，没有任何机制约束它们之和等于输入。三条估计各自带一点误差，相加之后误差也相加，峰值完全可能越过 1.0——尤其在鼓点和低音同时落下的那一瞬间。

        float32 回 int16：32767 和 32768 为什么不一样

        解码时用的除数是 32768，编码时用的乘数是 32767，这个不对称不是笔误，而是 int16 本身的范围就不对称：它能表示 −32768 到 +32767。除以 32768 解码，能让最负的那个整数精确落在 −1.0 上；乘以 32767 编码，能保证 +1.0 不会被 rint 推到 32768 而在转成 <i2 时溢出成负数。代价是一整趟往返之后，整条轨被乘上了 32767 / 32768。

        audio.T 是另一件必须做的事：内部所有数组都是 (channels, samples)，声道在前，因为按声道切片最顺手；而 WAV 的 data 块要求按帧交错存放，也就是 L R L R …，对应 (samples, channels)。转置之后 tobytes() 出来的顺序才是 wave 模块要的顺序。np.clip 也是在转置之后做的，两者合成一行。

        两个 WAV 去哪了，manifest 又是什么

        上传这一段有三件事在同时发生。第一件是写对象：put_output 只认请求里已经声明过的条目，取地址靠 output_item(output, name)，实际写入交给 put_output_item；换句话说，写到哪个 bucket、哪个 key、用哪个签名过的地址，全部由调用方在请求的 output 里给定（output_put_url 里的 access_url(item, field="output.<name>.access") 就是取那条预签名地址的），pipeline 自己不去拼 URL。这也是为什么 execute 一进来就先跑 validate_output_spec：名字必须正好是 manifest、background、vocals，content type 必须分别是 application/json 和 audio/wav，先卡住再干活，免得算完三分钟才发现没地方放。

        第二件是两种引用。两条音轨返回的是 legacy_object_ref：一份为老调用方保留的宽字段结构，把 bucket、region、key 摊开，再给出 public_url / internal_url / download_url，以及一个去掉 sha256: 前缀的裸哈希；internal_url 是拼出来的内网直连地址，好让同区域的服务不走公网。manifest 返回的是 result_ref，走 object_result_ref，带 content_hash 和 size_bytes——注意音轨那份引用里没有 size_bytes，两条路径的字段并不对称。

        第三件是 manifest。它就是把 output 这个字典本身用 sort_keys=True、紧凑分隔符序列化成 JSON，再当作第三个对象传上去。为什么要单独存一份：HTTP 响应是一次性的，调用方可能超时、可能重试、可能是另一个进程来收货，而 manifest 和两条音轨躺在同一个前缀下，谁拿到 key 谁就能知道这次分离产出了什么、每个文件的 sha256 是多少。sort_keys 加固定分隔符保证同样的 output 序列化出同样的字节，因此 manifest 的 sha256 是可比对的：同一个 run 重跑一次，如果内容真的一致，哈希也一致。而音轨的 sha256 是内容哈希，下游拿到文件后可以自己算一遍对上，用来确认下载没被截断、也没被中间层改写。

        响应里到底有什么

        execute() 用一个 try / except Exception 把整条流水线兜住，失败时不抛出，而是把结构化错误塞进 response_json 返回——这里的「兜底」是契约的一部分，不是坏味道。原因在于这是一个 BLS/Python backend 模型：它必须交回一个 InferenceResponse，而输出张量 response_json 是声明过的。如果让异常穿透，上游拿到的只是 Triton 层面的一段错误字符串，既没有 stage 也没有 retryable，更没有 elapsed_ms，编排层无从判断这次失败该重试、该换参数、还是该直接告诉用户。把失败也表达成一次成功的推理响应，是为了让失败同样可被机器读取。

        要注意它兜得有多宽：pb_utils.TritonModelException 也是 Exception 的子类，所以连「request_json 不是合法 JSON」这种校验失败也会走这一支，变成 status: "failed" 而不是 Triton 报错。同时 _error_payload 目前把 code 和 type 填成同一个值（都是异常类名），stage 是写死的字符串，retryable 恒为 false——上游不要指望靠这个字段区分「重试有用」和「重试没用」。

        本站收束两个对象、一份 manifest、一个带 summary 的 JSON，链路到这里闭合了。剩下的问题不再是「它能不能跑通」，而是「跑起来之后我该盯哪几个数」——summary 里那几项 ms 各自意味着什么，见 15 · 观测。

        所以第二个来源才是关键：/v2/models/<model>/versions/<version>/stats。这是个累计量端点，单看一次没有意义，用法是跑测之前抓一次、跑完再抓一次，两次做差，关心六个键：success、fail、queue、compute_input、compute_infer、compute_output。每个键都带 count 和 ns，相除就得到这一轮的每次推理平均值，代码里派生出来的两个是 triton_queue_per_inference_ms 与 triton_compute_infer_per_inference_ms。一个回答「等了多久」，一个回答「算了多久」，而 A 组的 infer_ms 是这两者加上 BLS 往返之后，从 Python 侧看到的墙钟时间。三个数对不上的时候，差额本身就是线索。

        判定链是有顺序的　代码按固定优先级往下走：先看运行是否失败，再看显存占比、内存占比，然后才是 queue / success，最后才轮到推理占比与下载回传占比。顺序是有意的：内存压满的时候，排队高只是结果不是原因。链上除了 0.20 还有几个写死的比值，但它们同属一类东西——单次跑动的初步指示，标签就叫 initial_indication。

        推导值：指标该是多大，可以先算出来

        把 metrics 当验收手段还有个更朴素的用法：先算出它应该是多少，再去看它是不是。段数由输入长度唯一确定，每段固定 4 次子推理，全程没有随机性，所以一条请求会在 Triton 账上留下多少次推理，可以事先算准。

        一条请求应当在 nv_inference_request_success 上留下多少次　下面每个数都由页面常量当场推出，属于推导值；右边没有对应的实测列，因为仓库里没有实测数据。

        这个量级本身就是个交叉验证手段：发一条三分钟的请求，四个 ONNX 模型的成功计数各自应该涨同一个数，pipeline 模型涨 1。如果某个模型涨得不对，说明取行的循环没有按预期跑满；如果计数完全没动，说明你抓的根本不是这个容器的 metrics。

        并发要怎么比

        单跑一次得不出饱和点，这一点 benchmark 文档写得很直白：同一段音频、同样的请求数，分别在 concurrency 1、2、4 各跑一个 case，然后横着比吞吐、p95 延迟、queue 时间和资源利用率，看吞吐从哪里开始不再随并发上涨、queue 从哪里开始吃掉延迟。还有一条硬门槛：成功请求少于 10 次时，p95 不稳定，不要拿它下结论——代码会把这句话直接写进结果的 limitations 里。

        这篇文章给不出任何性能数字　仓库里没有跑出来的 QPS、没有 p95、没有单次请求耗时、没有显存占用、没有饱和点，一个都没有。有的只是上面这套方法论、那条 0.20 的启发式，以及一个能把结果写成 JSON 上传的 runner。本站所有滑杆初值和堆叠条都是示意值；任何看起来像实测的数字，都不是。
        本站收束A 组告诉你慢在哪一段，B 组告诉你是在等还是在算，两组都对不上的时候才轮到猜。但观测回答的是「慢在哪」；当服务干脆不响应时，要问的是另一个问题——从看得见的症状，怎么退回到出问题的那一站。

        从症状回退到站：三级顺序，不许跳级

        出问题时最常见的浪费，是把网络问题、模型名问题和推理问题混在一起查：一边改 payload 一边怀疑显存，最后发现是 endpoint 拼错了。这条链路的排查顺序是固定的——先确认请求能不能到达服务，再确认目标模型是不是真的装载好了，最后才谈推理本身。每一级不通，下一级的所有报错都不可信。

        之所以能这么分级，是因为三级各自打的是链路上不同的一段：第 1 级只需要服务进程活着，第 2 级要求模型仓库被正确读取，第 3 级才第一次真正执行代码。跳级的代价很具体——在第 1 级没通的时候读第 3 级的报错，你读到的是网关的错误页，不是 Triton 的。

        三级决策树　先选层级，再从症状进入，下面给出真因、怎么确认、以及退回到哪一站。探针命令与鉴权细节属于 08 · 探针，这里只给判断动作，不重复那张命令表。

        第 2 级那个分叉，是整棵树里最值钱的一处

        当模型级 ready 返回不就绪时，先别急着看那个模型。把五个模型逐个探一遍，看是「全都不 ready」还是「只有一个不 ready」——这两种情况的根因完全不在一个层面上。

        全部都不 ready → 仓库根本没被正确读到
        OSS repository 的根目录填错了一层是最常见的：Triton 期望 --model-repository 的下一层直接就是模型目录，中间多一层包装目录，扫描结果就是空的。挂载失败、路径大小写不符、挂载点被别的目录盖住，症状都长这样。这时候去改某个 config.pbtxt 是纯浪费时间。
        只有一个不 ready → 就是这个模型自己的问题
        三种可能：config.pbtxt 里的 name 与目录名不一致（见 04 · 契约）；模型文件缺失或损坏；装载阶段报错——ONNX Runtime 解析失败、Python backend 的 initialize() 抛异常、CUDA 或显存不足。这三种在容器日志里长得完全不同，直接去读那几行装载日志，而不是继续在外面猜。

        把这个分叉放在前面，是因为它决定了接下来该看哪份东西：全不 ready 看部署与挂载，单个不 ready 看那一个模型目录和它的装载日志。判断只需要多发四次探针，省下的却是整轮方向错误的排查。
